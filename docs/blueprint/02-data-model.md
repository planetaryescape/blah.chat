# 02: Data model

## Conventions and scope

Use this chapter's names across clients, tools and migrations. The proposed records below are not present in the reviewed deployment merely because they appear here. Baseline: `04866f80a6236716ebf8d8c5a79001727f85f4bf`, reviewed on 2026-11-03. D-014–D-035 remain PROPOSED; [21](21-decision-log.md) records authority and [22](22-open-questions.md) records unresolved policies.

- Convex supplies `_id` and `_creationTime`. Foreign IDs are `Id<"table">`, not arbitrary strings. Provider request/tool/account IDs remain opaque external strings and never substitute for an app record ID.
- Instants are epoch milliseconds with `At` suffixes, except the canonical occurrence instant `scheduledFor`. Durations name their unit. New ordinals, sequences and versions are nonnegative integers; declared ordinal starting points are stable. HTTP `sys.timestamps` retain their existing ISO-string codec ([01](01-architecture.md)).
- Existing tables retain `userId`. New owner-scoped tables use `ownerUserId: Id<"users">`; this is not a rename of existing columns or a new tenant-organization abstraction. A denormalized owner/conversation reference must match its authoritative parent on every write. Run ownership identifies the admitted initiating principal; collaboration does not copy the conversation owner's private credentials to that principal.
- Keep normalized M:N junctions: participation, project/tag links, message-artifact references, schedule-version skills/connections and skill activation records. A reference from one child to one parent is not a junction. Ordered bounded snapshots such as DAG parent IDs or checkpoint coverage are not a replacement for independently mutable M:N associations.
- Model identity comes from the central executable catalog. Persist the resolved model/API/gateway/host/payer/catalog/pricing references, not only a friendly picker label. Version references resolve immutable server configuration, never secret material (D-035).
- Hashes use a versioned canonical serialization and a full collision-resistant digest, proposed SHA-256. Hash the validated semantic request, including owner scope, branch, options and pinned versions; exclude volatile timestamps/transport metadata. Same idempotency key with a different hash is a conflict, not a retry.
- Convex indexes are lookup/order tools. **There is no SQL `UNIQUE` enforcement implied by an index.** Every logical uniqueness rule below is an indexed read plus conditional insert/CAS in one Convex mutation. Duplicate delivery and concurrent transactions must be tested. `.unique()` reads do not create a constraint.
- Bound inline payloads. Text, screenshots, skill files and large tool output use private `contentRef`/storage references with MIME/byte/hash validation. Never persist a signed URL or public plot URL as the durable authorization mechanism.

The first repairs do not depend on this whole schema. [Incremental adoption](#adopt-only-the-records-a-release-needs) makes each capability add its own records (D-014, D-030).

### Canonical usage attribution

```ts
type UsageSubject =
  | { kind: "run"; runId: Id<"agentRuns"> }
  | { kind: "operation"; operationId: Id<"admittedOperations"> };
type UsageAttribution =
  | { kind: "run"; runId: Id<"agentRuns">; attemptId: Id<"runAttempts"> }
  | { kind: "operation"; operationId: Id<"admittedOperations">;
      operationAttemptId: Id<"operationAttempts"> };
```

Validators reject mixed/absent union members. An auxiliary call within a Run uses that Run's physical Attempt; standalone selection summarization/import authoring uses an admitted operation, never invented transcript rows. Admission derives the owner from authentication (or an already authorized durable internal principal), checks live owner/input ACL, policy, bounds and allowed payer, then atomically dedupes `(ownerUserId,clientRequestId)` against `requestHash` and reserves allowance when policy requires it. The semantic admission hash includes feature, validated input/source hashes, options, pins and payer policy. Identical replay returns the original operation; a changed hash conflicts. Optional real message references require a matching authorized conversation and are not execution authority.

#### Hosted ordinary-text settlement (Rung 6a)

The initial implementation adopts only interactive ordinary-text chat. `packages/backend/convex/chatSettlementSchema.ts` defines hosted `agentRuns`, `runAttempts`, append-only `usageEvents`, and derived `chatUsageProjections` metadata; these are not included by BYOD v37. A Run is keyed by its assistant message and initiating owner, including an authorized collaborator. Each generation invocation or separate continuation gets a new Attempt. The SDK V3 model middleware hashes canonical parameters after step preparation, persists dispatch identity before `doStream` or `doGenerate`, and captures each finish usage. URLs and binary inputs retain their values in the hash, but no raw input is stored. Adopted calls disable SDK retries. A stopped/failed dispatch with no finish remains unknown. The provider's token report and catalog-derived USD estimate are separate claims; a catalog estimate is not an invoice.

Usage evidence is grouped by the attempt/step/iteration `usageKey`. Repeated evidence keys are no-ops; a report supersedes an estimate in projections while both facts remain. Conflicting reported values require reconciliation. Each derived projection references a dedicated new `usageRecords` row with owner/date/conversation/model/feature/operation/payer dimensions, so existing monthly totals and budget readers include new chat usage without changing historical daily buckets. Corrections recognize only the difference, not estimate plus actual. Unknown steps do not hide another step's known subtotal. Context occupancy stays replace-only and separate from lifetime provider-token totals; SDK output includes reasoning rather than adding it twice. The public receipt query derives current authentication and checks the initiating owner and live message access. No receipt fields were added to the portable message schema.

Financial metadata survives conversation deletion: cascades detach the optional conversation and message references but retain the Run/Attempt/usage facts. Owner data erasure deletes the rows; a late settlement then fails because its dispatch identity no longer exists. This retention choice does not authorize transcript, prompt, tool-result, response-body, or credential retention. Incognito and standalone operation attribution remain outside 6a.

Allocate each physical auxiliary dispatch's immutable `(operationId,attemptIndex)` before network I/O, with exact request hash and actual payer/credential-version/pricing lineage. Physical retries get new Attempts; receipt/transport delivery replay does not. Operation cancellation increments its lease fence and forbids further dispatch/publication; terminal status is monotonic, but incurred usage still settles. No general continuation, tools or fabricated Run is required. Run attempts likewise retain exact dispatch request hash and credential-version lineage for the same accounting contract.

The canonical physical usage identity is the tagged attribution plus `stepIndex` and `iterationKind`; `usageKey` is its versioned canonical digest. Evidence rows use unique `evidenceKey = hash(usageKey, evidence source, stable receipt/revision identity, evidence hash)`; corrections retain the original `usageKey`, reference `correctsUsageEventId` and append evidence rather than mutate it. The indexed usage-key lookup returns the evidence group, not a falsely unique event. Settlement dedupes evidence and reconciles recognized deltas once ([14](14-cost-model.md)). A reservation's tagged subject must match attribution, owner, currency and policy; `reservationId` is required whenever reservation policy applies, otherwise absent with a policy-recorded reason. Admission and next-attempt reservation updates include outstanding Run **and** operation liabilities. One `usageEvents` writer owns both variants and derives legacy projections; these two minimal auxiliary identity tables are not another billing store.

`DispatchReceipt` is `{stepIndex:number, iterationKind:string, dispatchRequestHash:string, dispatchedAt:number}` with nonnegative integer step, centrally validated iteration-kind value and versioned canonical digest. Persist each physical SDK step's receipt in the owning Attempt's bounded `dispatches` array before dispatch, including later tool-loop steps whose input differs from the initial request. Transactional `(Attempt,stepIndex,iterationKind)` dedupe compares the hash; a changed physical request cannot reuse that identity. The entry records dispatch intent, not proof the provider accepted it. No provider receipt is needed to establish identity. Never overwrite an initial request hash with a continuation's hash. Standalone one-call Attempts use step0; route/payer/pricing changes require a new Attempt, not mutated lineage. Bound the array by the admitted step/iteration policy and stop before exceeding it. Unknown interrupted usage still references that receipt; corrections cannot change the physical request/payer. Reject mixed owner/parent/attempt lineage and conflicting evidence for the same source receipt revision before projecting any delta.

Invariants:

1. An owner/request key admits at most one run. Same hash returns original run/message IDs; a changed hash conflicts. Compare/admit/insert/reservation occur transactionally. Explicit comparison branches remain a named admission policy, not accidental concurrency.
2. `(runId, attemptIndex)` and `(attemptId, providerToolCallId)` are transactionally unique. Provider IDs are scoped to an attempt; persisted `toolCalls._id` is the app identity. A physical retry gets a new attempt; a transport replay does not.
3. `sequence` is monotonic within a run for tool calls and separately for run events. A producer must reuse its assigned sequence on delivery retry; the mutation checks `(runId,sequence)` and compares type/producer/payload before returning an accepted record. Different content at the same sequence conflicts. Do not allocate a fresh sequence for a duplicate or journal every token; persisted partial message content remains the refresh projection.
4. `effectOperationId` binds a logical effect across retries. Its owner-scoped lookup must compare exact inputs/account/version before reuse. It is not an exactly-once promise from the remote provider. `uncertain` outcomes require reconciliation, not automatic redispatch.
5. Approval requests bind exact effect, account, destination and input/content hashes. A response CAS checks owner, current interaction version, pending state, expiry, branch and policy. One accepted response commits one resume intent; duplicate delivery cannot dispatch another effect. A clarification answer never grants approval.
6. Accounting is independent of visible message status. Stop/failure still settles incurred usage once. Reported/estimated/unknown are not interchangeable; correction events preserve the original evidence and [14](14-cost-model.md)'s nonoverlapping projection semantics (D-016).

## Canonical state vocabulary

Do not add orchestration phases to these enums. Preparing, compacting, retrying and reconciling are events/reasons; `cancelRequestedAt` is a request, not another Run state (D-017, D-025).

```text
Run.status = pending | running | waiting_for_input | waiting_for_approval
           | succeeded | failed | cancelled

ToolCall.status = pending | running | waiting_for_input | waiting_for_approval
                | succeeded | partially_succeeded | failed | cancelled | unknown
ToolCall.effectCertainty = none | confirmed | uncertain

Interaction.status = pending | answered | denied | cancelled | expired | superseded

Artifact.status = creating | ready | partial | failed | cancelled | archived
ArtifactRevision.status = draft | committed | partial | failed | cancelled

SkillVersion.status = draft | validating | review_required | published | rejected
                    | superseded | disabled | revoked
SkillBinding.invocationMode = explicit_only | automatic_and_explicit | disabled

Connection.status = pending | active | reconnect_required | disabled | revoking
                  | revoked | failed
ConnectionAuthAttempt.status = pending | verified | failed | cancelled | expired
                             | superseded

Schedule.status = draft | review_required | active | paused | blocked | completed
                | revoked
ScheduleOccurrence.status = pending | running | waiting_for_input
                          | waiting_for_approval | succeeded | failed | cancelled
                          | skipped | blocked

ComputerSession.status = unallocated | allocating | ready | busy | pausing | paused
                       | resuming | reconciling | lost | terminating | terminated
                       | failed
ComputerAction.status = proposed | policy_checked | awaiting_approval | authorized
                      | dispatching | observing | succeeded | uncertain | reconciled
                      | denied | cancelled | expired | needs_user
```

Run terminal states are monotonic. Resume moves the same waiting run to `running`; it does not create a replacement run. A grant uses interaction `answered` with an exact allow decision; denial is `denied`. A receipt of consent is separate from successful execution. Computer action `uncertain` or tool `unknown` must not invent a `needs_reconciliation` Run state. The shared human wait is always `waiting_for_input`, never `waiting_for_user`.

### Message projection and old readers

The current message union remains exactly `pending | generating | complete | stopped | error`. Add **one optional `messages.runProjection` object**, proposed as:

```ts
// Additive definition; not current schema or implementation.
runProjection?: {
  runId: Id<"agentRuns">;
  status: RunStatus; // exact Run.status union above
  version: number;  // monotonically advanced by the server projection writer
  wait?: {
    kind: "clarification" | "approval";
    interactionId: Id<"interactions">;
    version: number; // interaction version, not projection version
    expiresAt?: number;
  };
};
```

| Run state | Existing message `status` | New reader behavior |
|---|---|---|
| `pending` | `pending` | Saved/queued, not unsent |
| `running` | `generating` | Show current persisted partials and actual activity |
| `waiting_for_input` | `generating` | Show clarification and paused state; no spinner/stale recovery |
| `waiting_for_approval` | `generating` | Show exact-effect review and paused state; no implicit approval |
| `succeeded` | `complete` | Saved result, possibly with separately unresolved tool-effect details |
| `failed` | `error` | Preserve partials and specific safe recovery |
| `cancelled` | `stopped` | Preserve partials/receipts; do not imply remote rollback |

Set `wait` only for a matching pending interaction in a waiting run; remove it transactionally on resume/terminal settlement. The query DTO must preserve explicit projection changes through payload compaction. Never add wait members to the old message enum or set `complete` merely to suppress a spinner.

Deploy recovery guards before enabling wait writers: a run-backed message is recovered only through its run/lease policy, not old message age. All supported clients must read the projection, show a non-authorizing fallback or be blocked from starting the new capability with an upgrade explanation. Existing old-client ordinary chat may continue; do not expose unsupported waits and hope it recovers. S8/S15 test this gate (D-025, D-031).

## Context is derived, not the transcript

`ContextPlan` is ephemeral and request-local. Its fields are `conversationId`, `branchHeadMessageId`, `transcriptRevision`, `contextEpoch`, resolved route/catalog/prompt/tool hashes, exact `messages`/`tools`, `inputTokens`, `countMethod`, `outputReserve`, `safetyReserve`, `toolGrowthReserve`, `usableInput`, `usableInputRatio`, and covered/retained IDs. Do not turn this into another durable transcript table (D-018).

`contextCheckpoints` stores `ownerUserId`, `conversationId`, `branchHeadMessageId`, immutable covered IDs/source hashes, `transcriptRevision`, `contextEpoch`, prior-checkpoint reference, summary ref/hash/schema/model, retained-tail boundary, cost/provenance and `createdAt`. Index `by_conversation_branch(conversationId,branchHeadMessageId)` and `by_owner(ownerUserId)`. An indexed coverage/hash lookup can dedupe the same plan, but publication still CAS-checks current transcript/epoch/head.

Coverage lists are bounded ordered provenance snapshots; large coverage must be chunked or referenced without exceeding Convex document/transaction limits. Validate every source belongs to the authorized branch. Increment transcript revision when durable eligible transcript material changes; change context epoch when a plan-invalidating branch/policy/context selection changes. Do not increment merely because a client reconnects. Late summary completion cannot publish over a changed branch, cancelled run or deleted conversation. Originals and recent atomic tool groups remain readable (D-018; [05](05-context-and-caching.md), S4).

Revision `author` is exactly `{kind:"human", userId:Id<"users">}` or `{kind:"agent", runId:Id<"agentRuns">, attemptId:Id<"runAttempts">, toolCallId:Id<"toolCalls">}`. Human actor/operation owner derives from authentication and current artifact/parent edit rights; agent operation owner derives from its initiating principal and proves live lease/cancel/terminal fences. Human revisions have no agent references and need no live Run, including after generation completes. Both enter the same hash-deduped revision writer/base CAS; no fake message association is needed for a human save. `currentRevisionId` may be absent while `creating`, but `ready` requires a committed owned revision. Commit checks `baseRevisionId` against current; a concurrent edit returns a conflict instead of overwriting another document. Once committed, content/hash/provenance are immutable; subsequent edits add a revision. Partial/failed/cancelled revisions remain distinguishable from committed answers (D-024).

Migrate prose→`document` and code→`code` only where existing `documentType` proves it. Canvas `active` does not become a new artifact state: map a validated saved document to `ready`, preserve archived state, and quarantine invalid data without fabricating a revision. Use old document/history IDs to derive stable migration operation IDs and reconcile version order. During coexistence, one artifact owner writes legacy canvas projections as needed; never let canvas and artifacts independently accept writes. Screenshot observations are restricted artifacts with private access/short retention policy, not public image links. HTML rendering does not widen access to referenced sources (D-024, D-028; [10](10-artifacts-and-interactions.md), S9).

| `scheduleVersionSkills`, `scheduleVersionConnections` | `scheduleVersionId` plus exact `skillVersionId` or `connectionId`/revision/grant reference | `by_version(scheduleVersionId)` plus reverse-resource indexes; normalized M:N pins; version/resource pairs checked transactionally |
| `scheduleOccurrences` | `scheduleId`, `scheduleVersionId`, `scheduleConsentId`, `admissionEpoch`, `executionRevocationEpoch`, `occurrenceKey`, `scheduledFor`, `status`, `runId?`, output refs, reason/details and timestamps | `by_schedule_key(scheduleId,occurrenceKey)`, `by_status_time(status,scheduledFor)`, `by_run(runId)`; one occurrence and at most one admitted run per key; admitted reviewed version/consent survives future-only pause/edit, never revocation |
| `notificationDeliveries` | Occurrence, owner, channel, deterministic delivery identity, outcome/retry receipt | `by_occurrence(scheduleOccurrenceId)`; delivery key checked in one mutation; notification retry never creates another agent run |

Skills are private until Q11 changes that policy; automatic discovery requires `automatic_and_explicit`, and a draft cannot publish itself. Connections are exact accounts, not toolkit-wide permission. A schedule's consent cannot propagate ambient auth, authorize arbitrary future writes or silently follow a newly published skill/account revision. All permissions are rechecked at execution. No legacy `scheduledPrompts` row arms automatically (Q11–Q17; [08](08-skills.md), [09](09-integrations.md), [12](12-schedules.md)).

For legacy Composio status mapping, `pending`/`initiated` remain a pending connection plus a separate pending auth attempt only while its stored state/expiry is still valid. An expired attempt becomes expired rather than a fabricated verified account. Existing `active` maps to active only with preserved exact remote identity and dispatch-time revalidation; `expired` maps to `reconnect_required`, and `failed` to `failed`. Never overwrite the retained active remote ID with an unverified reconnect attempt. A migration missing account/scope evidence must block dispatch and request verification, not infer permission from toolkit name (D-026).

## Computer records share the same authority

| Table | Minimum contract | Index / invariant |
|---|---|---|
| `computerSessions` | Owner, authorized run association, provider sandbox ID/template/version/resources, `status`, separate `desiredState`/`observedState`, creation/readiness/expiry/cleanup timestamps | `by_owner(ownerUserId)` and sandbox lookup; allocation operation is deduped before retry; sandbox ID is not an access token |
| `computerLeases` | Session/run/attempt, holder, monotonically increasing lease epoch, expiry/progress | `by_session(computerSessionId)`; one current controller via transactional CAS; viewers receive no controller authority |
| `computerActions` | Session/run/attempt, exact operation/input hashes, action status, policy result, shared `interactionId?`, dispatch/observation/effect certainty receipts | `by_session(computerSessionId)`, operation lookup; exact authorized effect cannot change after approval |
| `computerEvents` | Session/action/run association, bounded sequence/type/payload and timestamps | `by_session_sequence(computerSessionId,sequence)`; ordered evidence, not screen/video blobs |
| `computeUsage` | Session/run/attempt, stable provider event/interval identity, explicit resource allocation and measured/estimated/unknown quantity, pricing reference | Session/time and event-key indexes; no double counting interval and lifecycle totals; normalized into shared usage settlement |

Use `agentRuns`, `interactions`, `artifacts` and `budgetReservations` for work, decisions, outputs and limits. Do not add computer-only runs or approvals. Paused machines may persist disk/session data; `paused` is not deleted. An uncertain click/send stays an action outcome, not a reason to replay an entire desktop task. Live allocation is gated by Q3/Q4/Q15/S12 ([07](07-tools-and-computer.md), [13](13-privacy-safety-compliance.md), [14](14-cost-model.md); D-028).

## ACL, deletion and retention

Every query begins from an authenticated owner or an authorized parent conversation, then hydrates children. Denormalized `userId` filters and unguessable IDs are not authorization. Current participation allows shared conversation access; it does not grant private skill, credential, computer, schedule or effect-approval access. Owner-only new capabilities are the Q5 planning default. Public shares use a separate allowlisted DTO, never full row returns (D-014, D-022; permission matrix in [13](13-privacy-safety-compliance.md)).

No TTL is invented here. Q4/Q7 decide retention before new private-state writers ship. A long-lived key or usage ledger is not permission to retain prompt bodies forever.

| Data | Conversation deletion / account erasure policy proposed | Retention boundary |
|---|---|---|
| Messages, normalized attachments/tool outputs/sources, run events/interactions/checkpoints, artifact links/revisions | Shared domain cascade removes dependent private content. Retain a file/artifact blob only if an authorized independent surviving reference exists; otherwise enqueue reference-safe cleanup. | Existing ordinary content remains until explicit deletion/policy. New incognito extensions disabled until erasure is proven. |
| Independent files, notes, tasks and memories | Ordinary conversation deletion preserves current intentional keep/nullify behavior. Account erasure removes owned data, not another user's conversation merely because this user participated. | Smart Assistant removal never authorizes content loss; Q20 handles historical mappings. |
| Skills and pinned sources | Conversation deletion removes conversation-scoped binding/activation/source links without deleting independent owner library content. Account erasure removes owner versions/files/reviews. | Revocation immediately blocks execution; required historical reference retention must not leak executable access. |
| Connections and grants | Remove grants on parent deletion; account erasure disables execution first and persists remote revocation cleanup until resolved. | Local row deletion is not upstream OAuth revocation. Keep only necessary cleanup identifiers under Q4. |
| Schedules, consents, occurrences and deliveries | Revoke and fence callbacks before deleting dependent content. Remove/limit output refs per actual surviving parents. | Old callbacks cannot rearm; notification retry never regenerates deleted outputs. |
| Computer sessions/observations/export files | Deny ingress/control immediately; terminate/reconcile remote resources and erase private artifacts reference-safely. | Short-lived observation policy still Q4. Pause/snapshot/provider history are not erased by deleting the app row. |
| Usage/reservations | Settle incurred cost independently of deletion, then erase/de-identify private references under the agreed accounting/retention policy. | Preserve totals without prompt/tool content. No legal retention duration is assumed. |
| Local cache, trace exports, provider caches and backups | Emit authoritative erasure signal, purge local dependent records on reconnect, and document separately controlled retention/cleanup. | Filtering/list absence is not an erasure event; app deletion cannot promise processor/backup erasure. |

Use the existing [central cascade:14–148](../../packages/backend/convex/lib/utils/cascade.ts#L14), not the incomplete separate incognito/CLI loops. Add new domains to one dependency registry/helper as they ship. For bounded deletion, child cleanup and parent deletion may remain one mutation. For large accounts, add a resumable internal deletion job before claiming scale: mark `deletionRequestedAt` on the user/conversation, deny reads/new work, revoke shares/leases/grants, process indexed children in bounded batches, then remove parents and reference-safe blobs. These optional tombstone fields are additive proposals, not current schema. A delayed content writer requires an existing undeleted owner and every actual referenced resource parent; missing/deleting parents forbid recreation. Run-owned agent writes additionally prove current Run/Attempt lease/cancel/terminal fences; standalone asynchronous writes prove admitted operation/operation-Attempt fences without a fabricated conversation. Human artifact commits check current authenticated artifact/parent edit rights before the shared revision CAS, not an agent lease. Late financial/effect evidence uses its separately authorized idempotent ingestion/retention path without requiring a live chat or resurrecting erased content. Retain minimal cleanup/erasure evidence until retries and client synchronization are complete under Q4, without retaining erased content (D-022, D-032).

## Safe additive migration

1. **Inventory before writing.** Record active/modular/BYOD schema versions, stale clients, scheduled functions and in-flight run versions. Obtain scoped migration authorization. Produce a private dry-run report with counts, bad references, duplicate logical keys and blob-sharing cases. Do not inspect unrelated user content in logs (S17).
2. **Deploy permissive additive schema and compatible readers first.** New fields are optional for retained rows. Add required indexes before queries depend on them. Update modular definitions and regenerate BYOD schema/string artifacts; stage against an authorized deployment. Convex deployment validation is a release gate, not a claimed local check.
3. **Choose one writer per entity.** Enable new writes for a bounded cohort. Write compatibility fields/projections in the same Convex mutation as authoritative state. A legacy endpoint becomes an adapter to that writer, not an independent second writer. Network side effects are never dual-executed as part of dual-write migration.
4. **Dual-read with explicit precedence.** Prefer the new record only when its version/mapping marks that entity migrated; otherwise read old data through an ACL-equivalent adapter. Do not merge old/new arrays and double-count usage or show duplicate documents. Old clients read legacy projections; they do not get new authority through a fallback.
5. **Backfill bounded batches.** Reuse the existing `migrations` cursor/checkpoint mechanism ([schema:1471–1513](../../packages/backend/convex/schema.ts#L1471)). Stable source IDs and mapping keys make each batch idempotent. Re-read source revision before publication, preserve IDs/provenance, stop on conflict and reconcile references/counts/totals. Run twice against the same fixture: the second pass makes no semantic changes.
6. **Switch reads, then stop legacy writers.** Compare old/new projections and totals first. Verify stale clients and scheduled actions are fenced or upgraded. Keep legacy mappings/read support for the agreed window, Q20/Q22. Preserve old runner/policy/catalog/pricing versions for in-flight runs and history.
7. **Contract only after evidence.** Validate hosted and authorized BYOD deployments, backup/restore compatibility and retained-client behavior. Remove legacy fields/tables/generated references only when no supported writer or retained data requires them. Smart Assistant endpoint removal can happen before its final historical enum contraction (D-003, D-032).
8. **Rollback writers, not history.** Disable the new capability/admission first; let pinned old runs settle or cancel safely. Restore compatible reader/writer code without deleting new rows or contracting validators. Never replay remote effects or re-enable revoked grants during rollback. A security rollback must retain the endpoint protection.

Acceptance gates: S2 tests parent ACL across every alias; S3 tests dedupe/native results/all-attempt usage; S4 tests branch/version publication; S8/S15 test wait projection and old clients; S9 tests revision conflicts; S11–S13 test owner/version/occurrence isolation; S14/S17 test twice-run migration, cascade, restore and BYOD coexistence. Validate exact candidate schema and real validators with synthetic fixtures. None of these proposed tests has been run by this chapter (D-033).
