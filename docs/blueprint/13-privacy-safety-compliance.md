# 13: Privacy, safety and compliance

## Repair the reachable boundary first

Protect private reads and paid actions before expanding agent authority. The reviewed source has useful ownership checks, encrypted credentials, account-partitioned caches and fail-closed protected shares, but directly callable alternate Convex functions bypass some of them. UI authentication and Next middleware do not secure those functions. These are static findings at `04866f80a6236716ebf8d8c5a79001727f85f4bf`, reviewed on 2026-11-03, not evidence of production exploitation (D-014, D-022).

The policies below are PROPOSED unless inherited from the repository or explicitly requested by BK. Budgets, retention, collaboration and provider terms remain Q3–Q8; computer/skill/schedule authority remains Q11–Q17. Use synthetic fixtures first. This document authorizes no private-data inspection, paid call, remote exploit, migration or production action (D-001).

## One public admission policy

Every retained public path follows `identity → parent/resource ACL → validated bounded input → capability/payer/budget admission → internal work`. Identity is Clerk-derived or the existing verified CLI/API-key principal, not caller `userId`, `clerkId`, a model-supplied owner or an OAuth email. Keep JWT match checks and revoked-key handling. Internal helpers accept explicit trusted owner and caller-appropriate context: Run/Attempt for Run-owned agent work, admitted operation/operation-Attempt for standalone work, authenticated editor identity for human artifact saves. They still validate actual parent consistency and current policy; no variant fabricates a chat Run, and scheduled calls do not inherit user authentication ([02](02-data-model.md); D-014, D-017).

Apply the same rules to alternate send/regenerate/edit/merge/consolidation, image, summarization, embedding, speech and tool-internal LLM paths. Existing normal-chat admission is not a waiver for auxiliary APIs. Admission must happen before provider/storage work, not after a result returns. Bound raw bytes, serialized tokens, output, fan-out, concurrency, tool calls and wall time; Q3 must supply numeric paid-work limits before new autonomous jobs start. Missing configuration denies the new paid capability rather than meaning unlimited. Recorded monthly spend alone is not an in-flight dollar reservation (D-016; [04](04-durable-generation.md), [14](14-cost-model.md)).

At execution, recheck undeleted owner and actual resource parents, current grants/account revisions and exact approval binding where applicable. Run-owned agent dispatch/publication proves current Run/Attempt lease, cancellation and terminal fences; standalone asynchronous work proves its admitted operation/operation-Attempt fences and only real referenced parents. Human artifact saves require current authenticated artifact/parent edit rights before the shared revision CAS, not an agent lease. These checks belong immediately before dispatch/commit, not only when building a tool list. Late financial/effect evidence uses its separately authorized idempotent ingestion path without requiring a live chat or resurrecting erased content. Provider timeout or local abort can leave an external effect uncertain; preserve the operation/receipt and reconcile before retry. No browser dialog, generic chat yes, expired card or model text grants permission (D-017, D-025–D-029).

## Permission matrix

The current owner/collaborator read model comes from [`canAccessConversation:11–35`](../../packages/backend/convex/conversations/branching.ts#L11). Proposed new private capabilities default to the initiating owner alone, pending Q5. Membership in a chat does not grant use of another person's credentials or computer. “Internal” means a server entrypoint with a validated initiating principal and current policy, not blanket administrator access.

| Operation | Owner / initiating principal | Current collaborator | Valid public-share viewer | Anonymous, no valid share | Internal/scheduled executor |
|---|---|---|---|---|---|
| Read authorized conversation/messages/sources | Yes | Yes while active participant | Explicit share DTO/path only | No | Required purpose + parent ACL |
| Search private messages/files/projects | Own authorized scope | Explicitly authorized shared scope only; not owner's library | No | No | Same bounded scope; no caller-ID shortcut |
| Send ordinary shared-chat message | Existing authorized admission and actual payer policy | Existing authorized admission; never silently use owner's BYOK/connection | No | No | Admitted run/occurrence only |
| Read attachment/private artifact bytes | Parent plus explicit resource/reference access | Only conversation-authorized projection; no unrelated source/blob | Only separately approved publication DTO; initially excluded | No | Same resource check; restricted observations stay private |
| Edit artifact / capture a skill from shared data | Yes within owned resources | Not for new capabilities until Q5 | No | No | Exact authorized operation, not model intent |
| Answer new clarification | Initiating owner by default | No until Q5 | No | No | Cannot invent answer; may expire/cancel under policy |
| Approve external effect | Initiating owner, exact account/input/version | No until Q5 | No | No | Consume valid exact grant; cannot approve itself |
| Import/publish/use private skill | Own reviewed/pinned library and explicit binding | No implicit owner-library access | No | No | Exact owner/version/binding; script rights separate |
| Connect/reconnect/revoke account | Own account and verified auth attempt | No | No | No | Verified callback or cleanup outbox only |
| Arm/revise schedule | Own exact reviewed version and consent | No until Q5 | No | No | Fresh grant/policy each occurrence; cannot self-arm |
| View/control computer | Explicit owner/session grant; control separately leased | No until Q5 | No | No | Fenced lease/action policy; viewOnly is not ACL |
| Delete conversation/account data | Existing owner authorization | No deletion of another owner's chat merely through participation | No | No | Purpose-scoped shared cascade/cleanup only |

A removed participant immediately loses future reads, subscription updates, private byte access and dispatch authority. Existing issued storage URLs may have their own lifetime; do not promise instant revocation of an already downloaded copy. For new restricted artifacts/observations, prefer authenticated byte access or short-lived server-minted access after ACL checks, and test direct-object access rather than only hiding a card. [02](02-data-model.md) defines parent ownership and erasure fences (D-022, D-028).

## Public sharing is a separate projection

Current share queries return whole conversation/message rows, including the whole message tree; cached prompt disclosure is conditional on those fields being populated. This is a network-payload problem, not something CSS can hide ([shares:159–199](../../packages/backend/convex/shares.ts#L159)).

Proposed first policy, pending Q5: expose only the explicitly reviewed selected path or snapshot, not inactive siblings, private instructions, cached prompts, memory IDs, run policy/credential metadata, approval payloads, private skill sources, desktop observations or unrestricted artifact/source bytes. The exact path-versus-snapshot choice remains unresolved; do not silently widen existing shares during migration. Apply anonymization to actual DTO fields. Recheck active/expiry/revoke at every public projection and resource fetch (D-022, D-024).

Preserve password-bearing shares' current fail-closed behavior. A client boolean or a successful password dialog is not a server grant. Do not “repair” disabled protected shares by allowing their general public query. Seed private fields and inactive siblings, inspect response JSON and linked downloads anonymously, then revoke/expire and repeat; testing only the rendered page misses the leak (S2).

## Incognito means bounded persistence, not no processing

Current incognito already disables write tools/integrations and has configurable read tools/custom instructions. It still persists temporary conversation state, caches messages in IndexedDB and has an incomplete manual cleanup. An hourly/inactivity timer is not erasure proof ([tool gates:175–218](../../packages/backend/convex/generation/tools.ts#L175), [incognito deletion:65–165](../../packages/backend/convex/incognito.ts#L65), [local cache writes:198–215](../../apps/web/src/hooks/useCacheSync.ts#L198)).

Proposed contract (D-022; Q4/Q7):

- Keep server persistence required for refresh resilience, but state its lifetime and limits plainly. Incognito is not anonymous access, end-to-end encryption or a guarantee that processors retain nothing.
- Do not write incognito prompt/output/tool/attachment content into durable IndexedDB, long-lived speech caches, exported traces, explicit long-TTL provider caches or new durable skill/schedule/computer stores. New durable incognito extensions stay disabled until their erasure is proven. Temporary in-memory rendering is still data handling.
- Preserve read-tool and blank-slate/custom-instruction controls through scheduled owner lookup, request planning and model switching. A context summary must not quietly reintroduce memory or disabled instructions.
- Use one complete reference-safe cascade for manual deletion, expiry, CLI, REST and account erasure. Delete normalized children and unshared ephemeral blobs; preserve authorized independent copies according to policy. Fence late actions so they cannot recreate private rows after expiry.
- A permission/content/cache fingerprint includes owner/deployment, incognito/settings and relevant version/branch identity. Cache hit never bypasses current ACL. Reusing a provider prefix is not permission to load another user's content.

S2/S17 must inspect Convex children and all local cache tables after expiry while the detail page is unmounted, after refresh, and after a second offline client reconnects. No final local/provider TTL is asserted before Q4/Q7.

## Cache and deletion need the same owner

Preserve deployment+user partitioning and stale-identity fences in [`cache/db.ts:28–37`](../../apps/web/src/lib/cache/db.ts#L28), [`cache-provider.tsx:13–40`](../../apps/web/src/components/providers/cache-provider.tsx#L13) and [`messageTree.ts:22–85`](../../apps/web/src/lib/cache/messageTree.ts#L22). One global cache would regress isolation. Authenticated HTTP remains `private, no-store`, varying on authorization/cookie ([middleware:68–82](../../apps/web/src/lib/api/middleware/auth.ts#L68)).

Authoritative deletion must purge conversation/message/metadata/byte-cache dependents independently of a mounted detail hook. A filtered or paginated list missing a conversation is not proof of deletion. Use an explicit deletion signal or authoritative scoped reconciliation; apply it transactionally and resynchronize after offline periods. Account change closes old subscriptions/workers and prevents late writes to the new account partition (D-022).

The existing central cascade is useful but incognito and CLI bypass it: [central helper:14–148](../../packages/backend/convex/lib/utils/cascade.ts#L14), [CLI deletion:507–537](../../packages/backend/convex/cliAuth.ts#L507). Route all authenticated paths through the same domain policy. Ordinary chat deletion must not silently turn intentional independent file/memory nullification into wholesale deletion. Account erasure removes owned resources, not other owners' shared chats. Add new tables and remote cleanups as each capability ships, not after collecting their data ([02](02-data-model.md#acl-deletion-and-retention)).

Before deleting rows needed for remote cleanup, disable dispatch, revoke leases and persist the remote cleanup identities. Distinguish local disable, broker deletion, upstream OAuth grant revocation, sandbox termination, provider history and backup retention. Show pending cleanup truthfully; do not report universal erasure because the visible conversation disappeared. Reference-check shared blobs; retries are bounded and observable. Large-account batching, tombstones and restore behavior require S17 (D-022, D-026, D-028, D-032).

## BYOK and BYOD: state only what is verified

Keep randomized-IV AES-256-GCM credential encryption, internal-only full-credential reads and public presence booleans. Ciphertext is not suitable client data either. Keys, OAuth state/code and deploy credentials never enter prompts, artifacts, skill packages, tool-result cards or logs ([credentials:17–53,181–188](../../packages/backend/convex/byok/credentials.ts#L17), [encryption:21–51](../../packages/backend/convex/lib/encryption.ts#L21)).

Ordinary chat currently calls `getModel(modelId)` through environment-backed singleton clients without user-key resolution. The BYOK UI promise that all requests use the user's keys is therefore unsupported for this path ([generation:639–653](../../packages/backend/convex/generation.ts#L639), [registry:43–91](../../packages/ai/src/registry.ts#L43), [UI:332–336](../../apps/web/src/components/settings/BYOKSettings.tsx#L332)). Proposed repair: resolve payer/credentials server-side per request/attempt, do not mutate a shared singleton, reject missing/decryption-failed user keys before inference and never silently fall back to platform spend. Reuse the policy for auxiliary models, embedding and continuation; persist actual payer independently of user preference (D-016, D-035; Q8/S3).

BYOK changes credential/payer custody, not necessarily transport: app servers and any selected gateway/provider may still process content. Disclose the actual route rather than implying a direct client-provider connection. Two concurrent synthetic users with distinct mock keys must never cross clients or ledger payer identity.

BYOD settings, encryption and generated schemas exist, but full request-wide routing was not established. HTTP authenticated clients visibly target platform configuration in reviewed paths; helper presence is not end-to-end proof ([HTTP clients:24–78](../../apps/web/src/lib/api/convex.ts#L24), [audit gap](../../research_notes/blah-chat-modernization-review/data-security.md#gaps-1)). Before advertising “your database,” S17 must prove both WebSocket and HTTP/CLI paths, metadata/files/background jobs/migrations and deletion against two authorized staged deployments. Document what platform account/billing/auth state remains central. Do not quietly redirect a failed private deployment to hosted storage (D-022, D-032; Q8/Q20/Q22).

## New attack boundaries

Model output, retrieved text, tool results, HTML, skill instructions and desktop content are untrusted data. Boundary markers may guide a model; they are not authorization, sanitization or network isolation. Keep native structured results and enforce permissions outside the model (D-015).

|---|---|---|
| Markdown/code/math | Explicit sanitize schema/protocol/image policy in both React and worker paths; narrow math trust; bounded diagrams. Current custom Streamdown plugins replace defaults and omit the intended sanitize chain; no executable XSS was demonstrated. | Real parser/browser corpus and network checks, including 4,999/5,000/5,001 UTF-16 units; S6. [11](11-rendering-and-narration.md) |
| HTML artifacts | Separate isolated static preview. Disable scripts/forms/external assets/navigation; no same-origin app authority or credential access. Treat SVG/CSS/URLs/downloads and parent messaging as hostile. | Skills/imports | Validate archive paths, symlinks, sizes, YAML and manifest; quarantine before publication; scan/reject secrets; pin immutable package and files. It explicitly does not pin the checked IP, so DNS-rebinding remains a documented limitation ([urlGuard:53–118](../../packages/backend/convex/lib/urlGuard.ts#L53)). Preserve that honesty rather than presenting it as complete SSRF prevention. File IDs and signed URLs remain separate from upload provenance and access rights ([owned uploads:28–65](../../packages/backend/convex/http.ts#L28)).

## Data processors and user-facing promises

Maintain an actual data-flow inventory before enabling a new processor/region/TTL. No new vendor receives private chat data merely because it appears in a routing benchmark. Hosted-router evaluation starts with synthetic data; private eval export needs Q8/Q18 approval (D-019, D-022, D-034).

| Processor / location | Potential data | Required disclosure/control |
|---|---|---|
| Clerk | Identity/session/account metadata | Current auth scope; verified webhook/account erasure behavior |
| Convex and web host | Durable transcripts, normalized content, actions, HTTP/log metadata and storage | Actual deployment/backup/restore/retention map, private responses and owner ACL |
| Model/provider/gateway, speech and embedding services | Selected context/media/tool schemas and outputs; provider cache/history | Actual route/payer, retention/cache settings, allowed providers/regions and no unapproved fallback |
| Integration broker and upstream apps | OAuth account/scopes, selected tool inputs/results and external effects | Exact account, scopes, effect review, reconnect/revoke and pending cleanup |
| E2B | Selected files, script/desktop session state and observations | Explicit resources/retention/network policy, session isolation and terminate/cleanup behavior |
| Local browser/native storage | Cached conversation content, credentials handled by platform auth, exported files | Account/deployment isolation, incognito exclusion, deletion synchronization and deliberate exports |
| Telemetry/optional evaluation service | Allowlisted IDs, timings, classified errors; content only if separately approved | Redact before export, sample policy and retention; no incognito/raw prompt default |

Use metadata-first Pino logs and explicit correlation across Convex boundaries. Never log entire callback query parameters or raw provider bodies. The callback currently logs state-bearing params; safe presence/outcome metadata is enough ([callback:25–44](../../apps/web/src/app/api/composio/callback/route.ts#L25)). Sentinel state/code/token/key/prompt values must be absent from every test log sink, including errors and trace exporters. A failed export cannot fail a completed answer or become accounting truth (D-034; [15](15-observability-and-evals.md)).

No SOC 2, GDPR certification, zero-retention, end-to-end encryption or complete backup-erasure claim follows from this design. Exact obligations depend on actual users, processing and vendor terms. The immediate deliverable is a truthful privacy description plus working access, export/deletion and processor controls for the released features. Do not invent payment-webhook or enterprise tenancy work absent a validated product requirement.

## Acceptance and release gates

The following are requirements, not passed results (D-033):

1. **S1/S2: first security release.** Complete frozen-install scoped gates and every named public alias with owner, actual collaborator, outsider, revoked participant, anonymous and valid/expired/revoked share fixtures. 3. **S3: payer and authority.** Concurrent mock BYOK users stay isolated; anonymous/over-limit auxiliary calls cause zero spend; nested calls/stop/failure settle once.
