## Findings

| id | priority | issue | evidence file:line | impact | recommended action | confidence |
|---|---|---|---|---|---|---|
| BV-01 | P1 | Conversation shares can be created for conversations the caller does not own. The API accepts `conversationId` from the request and inserts a share without checking `conversations.userId`. | `apps/web/src/app/api/v1/shares/route.ts:8`, `apps/web/src/app/api/v1/shares/route.ts:31`; `apps/web/src/lib/persistence/conversationShares.ts:13`, `apps/web/src/lib/persistence/conversationShares.ts:27`; ownership field exists at `packages/persistence-postgres/src/schema.ts:136` | IDOR: a user who guesses/obtains another conversation ID can create a share row pointing at that conversation. Server metadata helpers dereference the shared conversation and first user message for `/share/[shareId]` metadata (`apps/web/src/lib/api/dal/shares.ts:34`, `apps/web/src/lib/api/dal/shares.ts:41`; `apps/web/src/app/share/[shareId]/page.tsx:9`). | Before inserting a share, resolve the authenticated user to the persistence user and require `conversations.id = conversationId AND conversations.userId = user.id`; add regression tests for cross-user share attempts. | High |
| BV-02 | P1 | Conversation share password protection is accepted by the API but not enforced, and passwords are stored as plain text. | API accepts `password` at `apps/web/src/app/api/v1/shares/route.ts:10`; storage writes it directly at `apps/web/src/lib/persistence/conversationShares.ts:35`; schema stores `password: text` at `packages/persistence-postgres/src/schema.ts:1706`; read helpers ignore password at `apps/web/src/lib/persistence/conversationShares.ts:128` and `apps/web/src/lib/persistence/conversationShares.ts:144`; UI says password-protected conversation shares are deferred at `apps/web/src/app/share/[shareId]/SharePageClient.tsx:163` | Users can believe a conversation share is password-protected while server-side share helpers do not check the password. Plain-text storage also exposes share passwords to DB/log/access compromise. | Either remove `password` from the conversation-share creation surface until implemented, or hash with bcrypt/argon2 and enforce verification before all metadata/conversation/message reads. | High |
| BV-03 | P2 | Public conversation share UI calls read endpoints that are not implemented. | Client calls `GET /api/v1/shares/${shareId}` at `apps/web/src/app/share/[shareId]/SharePageClient.tsx:74`, `/conversation` at `apps/web/src/app/share/[shareId]/SharePageClient.tsx:184`, and `/messages` at `apps/web/src/app/share/[shareId]/SharePageClient.tsx:195`; the only tracked share API files are `apps/web/src/app/api/v1/shares/route.ts`, `apps/web/src/app/api/v1/shares/[id]/route.ts`, and `apps/web/src/app/api/v1/shares/by-conversation/route.ts`, with `[id]` exporting only `PATCH` at `apps/web/src/app/api/v1/shares/[id]/route.ts:56`. | Shared conversation pages fail or hang for viewers. Combined with BV-01/BV-02, the sharing model is inconsistent: metadata helpers can read shares server-side, but client endpoints are absent. | Implement explicit public read/verify endpoints with authz/password checks, or remove/disable conversation sharing until complete. Add route tests matching the client URLs. | High |
| BV-04 | P2 | Clerk webhook signature verification uses parsed/re-serialized JSON instead of the raw request body. | `apps/web/src/app/api/webhooks/clerk/route.ts:26` calls `req.json()`, `apps/web/src/app/api/webhooks/clerk/route.ts:27` reserializes with `JSON.stringify`, and verification uses that string at `apps/web/src/app/api/webhooks/clerk/route.ts:34`. | Valid Clerk/Svix webhooks may fail verification because signatures are over the exact raw payload bytes. This can break user sync/delete handling and create auth/account lifecycle drift. | Read `await req.text()` once and pass the raw body to `Webhook.verify`; parse the verified event returned by Svix. Add a test that fails if JSON whitespace/key ordering changes. | High |
| BV-05 | P2 | Signed upload URLs allow arbitrary MIME types and have no visible server-side size/type policy. | Upload schema only requires non-empty strings at `apps/web/src/app/api/v1/files/upload-url/route.ts:8`; DAL passes caller-supplied `contentType` directly at `apps/web/src/lib/api/dal/files.ts:58`; signer constrains only `ContentType`, not size/content checks, at `packages/persistence-postgres/src/storage.ts:85`; file reads redirect to signed object URLs at `apps/web/src/app/api/v1/files/[...storageId]/route.ts:27`. | Authenticated users can upload oversized or active-content files, increasing storage/cost abuse risk and potentially serving unsafe content from the object-store origin. | Add allowlisted content types per upload context, max-size enforcement via presigned POST policy or app-side finalize validation, and safe serving defaults for active types (`Content-Disposition: attachment`). | Medium |
| BV-06 | P2 | Code execution endpoint lacks runtime schema/bounds for `code`, `language`, and `timeout`. | Body is destructured directly at `apps/web/src/app/api/code-execution/route.ts:117`; validation only checks truthiness at `apps/web/src/app/api/code-execution/route.ts:125`; `timeout` is only capped with `Math.min(timeout, 60)` at `apps/web/src/app/api/code-execution/route.ts:183`; arbitrary `code` reaches E2B at `apps/web/src/app/api/code-execution/route.ts:188`. | Authenticated users can send very large payloads, invalid languages, non-positive/non-numeric timeouts, and high-cost sandbox work within a coarse 20/hour limit. This risks DoS/cost spikes and brittle error behavior. | Add a zod schema with max code length, supported language enum, integer timeout range, and request body size limits; consider per-user/conversation quotas for E2B usage. | High |
| BV-07 | P3 | Security headers are missing CSP and Permissions-Policy in app-visible config. | `apps/web/vercel.json:15` sets global headers, but only `X-Content-Type-Options`, `X-Frame-Options`, legacy `X-XSS-Protection`, and `Referrer-Policy` are present at `apps/web/vercel.json:19`; repo search found no `Content-Security-Policy`. | XSS impact is higher in a rich markdown/code-rendering app; CSP is defense-in-depth, especially around `dangerouslySetInnerHTML` call sites such as `apps/web/src/components/chat/CodeBlock.tsx:114` and `apps/web/src/components/chat/MermaidRenderer.tsx:341`. | Add an incremental CSP, preferably report-only first, and a minimal Permissions-Policy. Avoid `unsafe-eval`/broad script sources unless documented. | Medium |
| BV-08 | P3 | Release auto-merge workflow trusts branch name + label after any successful PR CI without checking PR author/repo owner. | `workflow_run` trigger at `.github/workflows/release-please-auto-merge.yml:4`; merge condition only checks CI success and PR event at `.github/workflows/release-please-auto-merge.yml:16`; branch prefix/label check at `.github/workflows/release-please-auto-merge.yml:38`; merge runs with write token at `.github/workflows/release-please-auto-merge.yml:69`. | If a non-release PR obtains a `release-please--*` branch plus `autorelease: pending` label, this privileged workflow can approve/merge it after CI. Label control likely limits exploitability, but the workflow does not enforce the intended bot identity. | Also require PR author/app identity and head repo ownership, or query release-please metadata. Keep workflow write permissions scoped to the exact needed operation. | Medium |
