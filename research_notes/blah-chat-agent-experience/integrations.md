# Integrations: repair Composio or change provider?

Research date and access date for all external sources: **2026-11-03**. This is a proposal, not an approved provider selection. Scope is blah.chat's embedded, per-user integrations, not connecting this coding session to anybody's accounts. Inspection used application source, published SDK source, and live primary documentation. No provider authentication, account changes, installs, paid calls, or external writes were performed. Tests were inspected, not executed.

## 1. What is wrong with the current integration?

### Takeaway

The integration is incomplete in ways a provider replacement will not automatically fix. Preserve the existing authenticated ownership checks, per-chat opt-in, and incognito exclusion, but repair execution authorization, exact-account binding, reconnect, and remote revocation before enabling consequential tools broadly. [Selection](../../packages/backend/convex/composio/selection.ts#L13-L103), [execution](../../packages/backend/convex/composio/tools.ts#L59-L161), [reconnect](../../packages/backend/convex/composio/connections.ts#L96-L115), [revoke](../../packages/backend/convex/composio/oauth.ts#L413-L464).

### Cited findings

#### Existing design worth keeping

- OAuth initiation derives the user from authenticated Clerk identity, validates the integration against the local catalog, and consistently uses `blahchat_${user._id}` as the Composio user ID. Verification checks the local connection owner before querying the provider. This audit did not establish a cross-user account takeover. [OAuth initiation](../../packages/backend/convex/composio/oauth.ts#L65-L175), [verification](../../packages/backend/convex/composio/oauth.ts#L196-L266).
- New connections get 32 cryptographically random bytes of state with a ten-minute expiry. State travels in the callback URL; verification rejects missing, different, and expired state when the record has state. The callback uses authenticated Convex access, escapes serialized HTML data, and posts to an explicit configured origin. [State generation](../../packages/backend/convex/composio/oauth.ts#L10-L15), [callback URL](../../packages/backend/convex/composio/oauth.ts#L146-L160), [state storage](../../packages/backend/convex/composio/connections.ts#L91-L131), [verification](../../packages/backend/convex/composio/oauth.ts#L237-L252), [callback HTML](../../apps/web/src/app/api/composio/callback/route.ts#L107-L137).
- **Connections are now opt-in per user and per chat.** No selection rows means no external tools. Selection checks conversation access, connection ownership, active status, and incognito; generation reads that selection query. Do not repeat the older interpretation that every active connection is automatically enabled in every chat. [Schema](../../packages/backend/convex/schema.ts#L1739-L1748), [selection](../../packages/backend/convex/composio/selection.ts#L13-L35), [generation](../../packages/backend/convex/generation.ts#L399-L427), [selector UI](../../apps/web/src/components/chat/IntegrationSelector.tsx#L17-L118).
- Incognito also excludes Composio during tool assembly. Result wrapping labels remote content as data, and tool names are normalized for provider compatibility. Those are useful protections, but data labels are not a security boundary against prompt injection. [Assembly and result wrapper](../../packages/backend/convex/generation/tools.ts#L277-L354).
- The credential model is brokered: the local schema stores remote connection IDs and optional scopes/state, not provider refresh tokens. Composio Cloud holds provider credentials and performs authenticated execution. This keeps tokens out of normal model context but makes Composio another processor of tool arguments/results. [Schema](../../packages/backend/convex/schema.ts#L1750-L1775), [current custody documentation](https://docs.composio.dev/docs/security/token-custody.md).

#### Prioritized defects and repair requirements

Priorities are proposed engineering priorities. Confidence is high in the cited code mechanisms; production incidence and live provider behavior were not measured.

| INT-01 / P1: no per-operation authorization or confirmation | Once an app is selected, the wrapper executes each retrieved tool directly. There is no local read/write/destructive allowlist, target restriction, approval check, or durable effect admission in this wrapper. Connection consent is therefore being used as permission for whatever write tools discovery returns. | INT-03 / P1: reconnect overwrites the working account before success | `createConnection` preserves `status: active` during re-auth, but immediately replaces `composioConnectionId`, scopes, and state with the new pending attempt. Distinguish "disabled in blah.chat" from "provider cleanup confirmed." Use the same outbox for account deletion. Test provider 500/no API key, direct public-mutation calls, old reconnect accounts, and repeated cleanup. Verify separately whether provider deletion revokes the upstream grant or only removes broker credentials. |
| INT-05 / P1 functional: mobile never completes local verification | Mobile opens `blahchat://composio/callback`, discards `openAuthSessionAsync`'s result, and never calls `verifyConnection` with the returned account/state. A successful upstream flow therefore has no visible path here to turn a new local `initiated` record into `active`. [Mobile](../../apps/mobile/app/(drawer)/settings/integrations.tsx#L75-L98), [verification requirement](../../packages/backend/convex/composio/oauth.ts#L190-L280), [HTTP router](../../packages/backend/convex/http.ts). | Handle the auth-session result through an approved callback/deep-link design, then verify ownership and attempt state server-side before showing success. Test success, cancel, application restart, expired state, wrong user, and intercepted/replayed links on actual supported platforms. |
| INT-06 / P2 security hardening: callback/attempt validation is incomplete | Both initiation and refresh accept an arbitrary `redirectUrl` string and append state; the HTTPS check exists only in the web hook. Backend verification accepts legacy state-less records, and successful status updates never consume/clear stored state. The web message listener checks origin/type but not `event.source`, expected connection ID, or attempt ID. These are gaps, not a demonstrated bypass of the existing authenticated owner check. [Action inputs](../../packages/backend/convex/composio/oauth.ts#L65-L70), [refresh](../../packages/backend/convex/composio/oauth.ts#L323-L405), [state validation](../../packages/backend/convex/composio/oauth.ts#L237-L252), [status update](../../packages/backend/convex/composio/connections.ts#L162-L168), [listener](../../apps/web/src/hooks/useComposioOAuth.ts#L38-L75). | Use server-owned exact callback allowlists per environment/platform. Keep required state on new attempts and retire legacy exceptions through an explicit migration. Consume attempts atomically after verification, checking remote user/toolkit/auth-config identity as defense in depth. Bind messages to the expected popup, connection, and attempt; trust the durable connection state, not the toast. Test arbitrary callbacks, same-origin unrelated windows, replay, simultaneous tabs, and legacy records. |
| INT-07 / P2: connection caps are bypassable | New initiation counts active accounts outside the create mutation, not pending reservations. Existing records skip the check. The exported `refreshConnection` action can create a record without requiring an existing connection or checking the limit. Concurrent pending flows can also exceed the intended active cap. [Admission](../../packages/backend/convex/composio/oauth.ts#L96-L129), [refresh](../../packages/backend/convex/composio/oauth.ts#L323-L399), [upsert](../../packages/backend/convex/composio/connections.ts#L96-L131). | Centralize admission in a transaction with pending reservations, expiry, and rate limits. Refresh must require an owned existing account. Test simultaneous activation, repeated cancelled attempts, and direct refresh for an unconnected app. |
| INT-08 / P2: auth configuration is not controlled or reproducible | A process-local map has no TTL/invalidation. Cache misses choose the first auth config returned for a toolkit, regardless of expected app, scopes, enabled status, or environment; listing errors fall through to creating a managed config. No scopes are supplied to creation or persisted by OAuth callers. A deleted cached config will not invalidate merely because a later initiation fails. [Config helper](../../packages/backend/convex/composio/oauth.ts#L17-L58), [create call](../../packages/backend/convex/composio/oauth.ts#L163-L175), [optional scopes](../../packages/backend/convex/composio/connections.ts#L81-L90). | Configure reviewed auth-config IDs explicitly per environment/app/scope profile. | INT-09 / P2: discovery is broad, truncated, and repeated | Every tool build fetches up to 100 tools across selected toolkits with no task search, scope filtering, pagination, or application schema cache. | INT-10 / P2: token health is guessed from exception text | Only thrown `Error` messages containing lowercase `expired`, `401`, or `unauthorized` mark an account expired. Structured `successful: false` results are returned without classification; the SDK explicitly models these as ordinary result values. ### Inferences

- The poor trial experience is plausibly explained by application defects before any catalog-quality problem: mobile cannot visibly finish verification, discovery can omit the desired action, stale auth configs are chosen implicitly, and re-auth can lose the known working account. Which one BK actually encountered remains unknown.
- The earlier generation finding about cancellation still applies to this executor. However, its older generalization about universally active integrations must be narrowed because current generation uses per-chat selection. [Earlier generation analysis](../blah-chat-modernization-review/generation.md), [current selection call](../../packages/backend/convex/generation.ts#L422-L427).
- Repair the existing application contract before measuring providers. Otherwise a migration can reproduce the same unsafe write behavior, false "connected" states, oversized results, and unrecoverable disconnects with a different SDK.

### Gaps

- BK's failed trial, desired apps/actions, actual connected accounts, provider dashboard auth configs, current billing contract, granted scopes, production approval status, and refresh histories were not accessed.
- Remote native-tool account-selection ordering was not verified. The missing explicit account binding is confirmed; a specific wrong-account production event is not.
- Whether Composio account deletion revokes an upstream OAuth grant, how long backups retain data, and whether orphaned accounts already exist require provider-specific verification. Do not label local row deletion "full revocation."
- No real OAuth, popup, mobile, concurrency, or send/revoke test ran. Edge CSP, referrer policy, provider callback constraints, and other infrastructure controls were not observed.

## 2. Which current alternatives fit a personal-first, multi-user agent app?

### Takeaway

Composio is no longer the only credible option, but current Composio also has capabilities absent from this old integration. Nango now provides agent sessions, catalog tools, and remote-MCP aggregation, so describing it as only OAuth plumbing would be outdated. Pipedream Connect is the strongest broad-catalog alternative to include if its production minimum is acceptable; Arcade is attractive for execution policy but has important multi-user auth and data-policy costs. [Composio sessions](https://docs.composio.dev/docs/configuring-sessions.md), [Nango sessions](https://nango.dev/docs/guides/agent-sessions.md), [Pipedream Connect](https://pipedream.com/docs/connect/mcp/developers.md), [Arcade production auth](https://docs.arcade.dev/en/build/user-facing-agents/secure-auth-production).

### Cited findings

#### What is actually being purchased?

OAuth plumbing supplies consent, credential custody, refresh, and reconnect. An agent tool platform additionally supplies action definitions, discovery, argument validation, execution, and often logs/permissions. A remote MCP server supplies a protocol interface; it does not by itself supply secure account isolation, consent UX, read/write confirmation, or reliable effect handling. All shortlisted services now cover more than bare OAuth, but the ownership boundaries differ. [Nango auth](https://nango.dev/docs/guides/auth/auth-guide.md), [Composio custody](https://docs.composio.dev/docs/security/token-custody.md), [Merge architecture](https://docs.merge.dev/merge-agent-handler/how-it-works), [MCP security specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices).

#### Production OAuth approval and migration are real work

- Composio managed apps are valid for production when scopes, branding, and shared quotas fit; custom apps are needed for changed scopes, own quota/branding, or some custom instances. The pricing page recommends moving to own apps before scale. Pipedream officially permits managed-client prebuilt tools/proxy in production but **credential retrieval requires a custom OAuth client**. Neither statement means every catalog entry has a managed production OAuth app. [Composio managed/custom](https://docs.composio.dev/docs/authentication/custom-app-vs-managed-app.md), [Composio pricing](https://composio.dev/pricing), [Pipedream client matrix](https://pipedream.com/docs/connect/managed-auth/oauth-clients.md).
- Nango now offers managed OAuth apps that can be used in production where available, plus own-app configuration. Application ownership mapping still lives in blah.chat; tags are selectors, not evidence of an authenticated end user. Arcade's default apps have the stricter project-member verifier restriction described above. [Nango auth guide](https://nango.dev/docs/guides/auth/auth-guide.md), [Arcade production guide](https://docs.arcade.dev/en/build/user-facing-agents/secure-auth-production).
- An own-app Gmail reading feature can entail Google's sensitive/restricted-scope verification. Restricted-scope data transmitted/stored through servers may require a security assessment, subject to documented exceptions including personal/internal/testing use. A personal prototype's exception is not a public multi-user launch approval. Minimize the exact scope set and verify the policy against the intended feature. [Google's restricted-scope requirements](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification).
- Composio's current connected-account reads redact usable credentials; its docs explicitly say these are **not a supported token-export workflow**, even for custom auth configs. Thus moving existing connections is not "export rows and import tokens." Nango documents credential retrieval, while Pipedream restricts it by OAuth-client ownership. Budget for explicit user reconnect unless a supported transfer is confirmed with both providers and the upstream OAuth app remains compatible. [Composio custody/export boundary](https://docs.composio.dev/docs/security/token-custody.md), [Nango credential access](https://nango.dev/docs/guides/auth/auth-guide.md), [Pipedream matrix](https://pipedream.com/docs/connect/managed-auth/oauth-clients.md).

#### Data processing, revocation, and events

- Composio stores execution arguments/results in logs by default. Its project ZDR prevents storage of covered new call payloads, not processing, historical-log deletion, or blah.chat/LLM logging. KMS/private/self-hosted arrangements are distinct commercial architectures; "bring your OAuth app" does not remove Composio from token custody. [Custody and retention boundaries](https://docs.composio.dev/docs/security/token-custody.md).
- Nango documents 15-day Cloud operational-log retention, no request/response bodies in proxy/API-call logs, immediate connection inaccessibility on soft deletion, and hard deletion 31 days later. Logs/audit history age out separately; immediate regulatory purge requires support. Current pricing says no EU public cloud, with regional BYOC on Enterprise. [Security/retention](https://nango.dev/docs/guides/platform/security.md), [regional FAQ](https://nango.dev/pricing). This is more specific than "open source means no processor risk."
- Nango refreshes OAuth tokens before expiry, retries transient failures, and can notify the app of failure and recovery. This gives a better lifecycle contract than treating any occurrence of `401` as permanent expiration. [Refresh documentation](https://nango.dev/docs/guides/auth/token-refreshing.md).
- Pipedream distinguishes connection-success/error webhooks from trigger webhooks. Its documented HMAC-SHA256 signature and timestamp replay protection are for **trigger deliveries**; do not assume that the same signature contract covers connection callbacks without checking. Connection completion should be reconciled server-to-server against the pending token/user/account. [Webhook documentation](https://pipedream.com/docs/connect/webhooks.md).
- Merge documents US-East hosted storage, 90-day default audit retention, user-scoped keys, separate credential revocation versus full registered-user deletion, and no server-side tool-result cache. Enterprise residency and custom deployments are contractual. [FAQ](https://docs.merge.dev/merge-agent-handler/resources/faq).

### Inferences

- **First proposal: keep/repair, then compare, rather than migrate immediately.** Composio's current pricing and existing connected-user footprint favor a repair-first baseline. This is conditional on BK's target actions working reliably and accepting the broker's data policy. It is not an endorsement of the old implementation.
- **Run Nango as the primary challenger.** Its exact-connection sessions, scoped agent token, explicit proxy-off default, credential access, and free small-account allowance fit this app. Current automatic catalog updates and newly expanded session features need real tests; the docs alone do not prove better tools.
- **Include Pipedream if broad coverage is important or Nango's target actions underperform.** Its production minimum is likely the decisive downside for a personal-first app, not its connector count. An annual quote is not a monthly-cancellable $99 plan.
- **Promote Arcade only if its tested action quality/policy pays for the extra OAuth/verifier work and the data contract is acceptable.** No-training consent and log controls are launch requirements for this use case, not optional housekeeping.
- Paragon and Merge become more persuasive if the product changes toward B2B embedded integrations, organization-shared credentials, data sync, or centrally governed enterprise agents. Their strengths do not establish economic fit for today's personal-first brief.
- Different providers may win individual apps. A narrow neutral adapter plus one exceptional official MCP/custom connector is more realistic than trying to maintain a universal cross-vendor schema for every action.

### Gaps

- No vendor's action success rate, p95 latency, callback completion rate, refresh reliability, scope correctness, mobile UX, or support response was independently benchmarked. Connector/tool counts and vendor claims of reliability were deliberately not used as quality evidence.
- Paragon production quote, exact semantic-search behavior, and detailed retention/deletion contract remain unverified. Merge semantic progressive disclosure and current connector-specific account-selection behavior also need confirmation.
- Arcade's default training consent, recommendation billing, paid feature entitlements, and multiple-account semantics require confirmation. The documentation establishes an opt-out model, not the current setting on a prospective account.
- No provider guarantees exactly-once remote writes across a lost response in the inspected evidence. Any automatic retry claim needs endpoint-specific idempotency or reconciliation tests.
- The public prices are not the old Composio account's contract. No account/billing access was used to resolve that uncertainty.

## 3. What should be demonstrated before deciding, and how can migration preserve consent?

### Takeaway

Choose against a small sandbox workflow and explicit safety gates after BK names the target apps. Keep provider choice outside the model, make every external account/action grant explicit, and preserve one execution owner for each operation during coexistence. The current app already has useful default-off chat selection to build on. [Current opt-in](../../packages/backend/convex/composio/selection.ts#L13-L35), [account-binding gap](../../packages/backend/convex/composio/tools.ts#L50-L65).

### Cited findings

- Current Composio sessions can restrict toolkits, tools, auth configs, and exact connected accounts, but the unrestricted default includes the whole catalog. Merely setting approval lists does not restrict availability. Meta-tool groups and proxy/workbench capabilities need separate configuration. [Configuration reference](https://docs.composio.dev/docs/configuring-sessions.md).
- Current Nango sessions let the backend pin connections/tools, keep general tools searchable, disable proxy/create-connection meta-tools, and terminate scoped sessions. Ending a session **does not cancel an already-in-flight call**. Its 5 MB remote-MCP cap is far too large to treat as an LLM context budget. [Sessions](https://nango.dev/docs/guides/agent-sessions.md).
- Arcade explicitly says recommendation is not authorization, and its REST execute endpoint is not limited to the gateway supplied to selection. This is a concrete reason that a provider-neutral app must check allowed tool/account/operation again at dispatch. [Recommendation contract](https://docs.arcade.dev/en/operate/governance/mcp-gateways/tool-recommendation).
- Langfuse datasets support structured inputs/expected outputs, metadata, versioned datasets, and comparable experiments. This can organize the proposed benchmark without putting real mailboxes or auth URLs in traces. No dataset or trace collection was created here. [Current dataset documentation](https://langfuse.com/docs/evaluation/experiments/datasets).
- Remote MCP adds authorization-URL and metadata-discovery SSRF concerns. The MCP security guidance also requires short-lived single-use OAuth state, exact registered redirects, audience validation, and explicit consent for proxy relationships. Adopting MCP does not remove OAuth responsibilities. [MCP security guidance](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices).

### Inferences

#### Proposed minimum vertical demo

Use **one sandbox mailbox**, initially Gmail only if BK confirms it is a priority; otherwise use the chosen service's closest read/draft/send equivalent. Add a second user and second account to test boundaries. A GitHub test repository or private Slack test channel can be the next app, not fifty catalog tiles. All writes below are a future, explicitly authorized test plan. **No send, draft creation, connect, or revoke was performed in this research.**

| Step | What the demo must show | Pass condition |
| --- | --- | --- |
| Connect | Signed-in user connects the selected sandbox account through a server-created attempt. Show provider, account, scopes, expiry/reconnect status, and which data processors receive content. | Callback must match owner, account/toolkit, expected callback, state/attempt, and expiry. Another user, another pending attempt, replay, cancellation, or wrong account cannot promote it. Display success from durable verification, not `postMessage` alone. |
| Read | User opts this account into one non-incognito chat and asks for one seeded test thread. | Only approved read tools appear/discover; execution checks policy again. Other accounts/users/chats remain inaccessible. Return sender/date/subject/snippet plus authorized result reference, not all mailbox content. |
| Draft | Agent proposes a reply in the app. Prefer a local draft first; saving a draft into the provider is itself an external write and requires its own grant. | No send tool runs. Preserve exact account, recipient, subject/body, attachments, and referenced thread. Let the user edit the proposed content. |
| Confirm | Server persists a pending operation with canonical input hash, tool/schema/policy version, account, authenticated approver, conversation/run/branch, destination, expiry, and unique operation ID. | An explicit UI shows the complete irreversible effect. Changing recipient, body, attachments, account, or tool invalidates approval. Text inside email/tool results cannot approve it. Denial/expiry yields no remote write. |
| Send | Only after a separate explicit user authorization, send one known message to an allowlisted sandbox recipient. In the initial automated suite, mock transport or use a provider-supported no-effect path. | Exactly one approved operation dispatches. Revalidate live connection and policy immediately before it. Persist provider message ID/outcome. On timeout after possible dispatch, show `unknown` and reconcile instead of silently retrying. A disabled real-send button is a valid first demo milestone. |
| Revoke | User disables the integration, pending operations, and sessions; remote cleanup runs through an outbox. | Immediate future-call denial, cache/session invalidation, visible cleanup status, retries until confirmed deletion. Reconnect never restores former chat grants or approvals implicitly. Explain that sent mail cannot be recalled and historical chat content is a separate retention decision. |

The send path needs a persisted state model such as `pending -> approved -> executing -> succeeded | failed | unknown`, with denied/expired/cancelled alternatives before execution. Atomic approval consumption prevents two local dispatches, but it cannot prove exactly-once behavior in the remote service. Use source endpoint idempotency when available; otherwise reconcile by provider object/operation evidence before offering another send.

#### Proposed small benchmark

After BK approves target apps and data handling, compare repaired Composio with Nango; add Pipedream or Arcade only if the shortlist has a specific coverage/policy question. Do not fund or authenticate all six platforms just to make a comparison table.

Start with 10 reviewed fixtures, not a large judge-generated corpus:

1. Connect/read the seeded sandbox item with minimum reviewed scopes.
2. Wrong user/account/tenant and mismatched callback state.
3. Two simultaneous auth attempts; cancel reconnect while the original account still works.
4. Missing action or insufficient scope; fail truthfully without proposing broader scopes silently.
5. Expired token, transient refresh failure, successful recovery, and permanent revocation.
6. Multi-page/large result, attachment, missing cursor, and provider output-shape drift.
7. Prompt-injected email/document attempting a send or data exfiltration.
8. Draft and edited confirmation; replay/expired approval and two simultaneous consumers.
9. Stop/revoke during a silent call and a remote-success/lost-acknowledgement write.
10. Disconnect/account deletion during provider outage, then reconciliation and rollback.

Run deterministic adapter/HTTP fixtures without an LLM first. Then run the same human-reviewed task prompts through representative configured models with matching tool policy and sandbox data. Record SDK/toolkit versions, scope profile, schema hash, provider region, model ID, cold/warm state, and exact fixture version. Assess hard security gates separately from answer quality; do not use an LLM judge to certify account isolation or no-send behavior.

Proposed decision measures:

- Zero unauthorized cross-user/account calls, unapproved writes, or duplicate effects in the adversarial suite.
- Read/draft task completion, correct-account execution, reconnect completion, cancellation/revoke correctness, missing-action rate, and error specificity.
- p50/p95 connect/discovery/execution latency, cold versus warm start, definition tokens, result tokens/bytes, model/tool turns, provider/API/LLM costs per completed task, and refresh-related failures.
- Time spent registering production OAuth apps, changing scopes, repairing one broken action, diagnosing one failed call, and completing remote deletion. These maintenance hours may matter more than a small per-call price difference.

Set numeric latency/success thresholds with BK after a small baseline. Select a replacement only if it passes the hard gates and improves the actual target workflows enough to justify reconnect and maintenance cost. If repaired Composio works, keeping it is a valid outcome.

#### Result budgets and caching belong in blah.chat

Proposed application policy, regardless of provider:

- Expose a small stable core tool set and search only the authorized catalog when more is needed. A useful initial experimental budget is 5-10 relevant tools at a time, with a measured definition-token cap. Search ranking is not authorization; an unreturned tool must still pass execution policy.
- Cache token-free definitions by provider, environment, toolkit/version, schema hash, and policy profile. Keep per-user selected-account grants and executable closures out of shared global caches. Rebuild runtime bindings from live authenticated state.
- If read-result caching is justified, key it by user/tenant, provider, exact account, granted-scope/policy revision, tool/version, canonical arguments, and cursor. Use short task-appropriate TTLs, bounded storage, provenance/freshness metadata, and explicit invalidation on write, revoke, reconnect, or policy change. Never cache send results as a substitute for an operation ledger.
- Propose a small default model-visible result budget, for example 8,000 tokens per call, to validate in the benchmark. Apply byte limits before JSON parsing where possible, bounded records/pages, selected fields, and authorized artifact storage for the rest. Include source IDs, `truncated`, cursor, and fetch time. Large-result workbenches are a separate execution/data-retention decision, not a default fix for bloat.
- Treat email bodies, documents, names, schemas/descriptions from unreviewed MCP servers, and tool results as untrusted data. Application allowlists, constrained inputs, exact-target approval, and durable dispatch checks must remain effective even if the model follows an injected instruction.
- Record sanitized spans for connect/discover/execute/approve/revoke/reconcile with correlation IDs, versions, typed outcomes, latency, counts, and metered cost. Do not collect raw mail, recipients, OAuth query strings, session URLs, or credentials into Langfuse/provider/application logs by default. Synthetic test data can supply the initial evidence.

#### Coexistence, migration, and rollback proposal

1. **Define the product contract first.** BK chooses the first 2-3 apps, read versus draft versus send behavior, whether multiple accounts are needed, and acceptable data-processing regions/retention/training terms. Inventory existing remote account IDs and OAuth app ownership using authorized access later, without exporting tokens into research notes.
2. **Repair lifecycle and add the application boundary while retaining Composio.** Introduce provider-neutral connection records and authorization-attempt records with provider, environment, local owner, opaque remote user/account ID, scope profile, account display identity, status/revision, and cleanup state. Preserve the existing per-user/per-chat opt-in semantics. Put provider-specific mapping behind `connect`, `verify`, `discover`, `execute`, `health`, and `revoke` adapters; do not attempt to normalize every vendor action's business schema.
3. **Separate consent levels.** OAuth scopes, application account grant, chat selection, allowed tools/resources, and operation-specific approval are separate records. Explicitly selecting an integration is not permission to increase scopes or switch a personal account to a shared company credential. Disable proxy/workbench/general-execute routes unless their equivalent restrictions are enforceable.
4. **Sandbox coexistence behind backend routing flags.** New provider connections are additional opt-in records, not replacements of old IDs. Route each chat/account operation to exactly one provider/version. Catalog comparisons and fixture reads can run in parallel if authorized; do not shadow real sends, creates, deletes, or draft writes. A provider outage must not cause the model/router to fall back to another account.
5. **Handle portability honestly.** Default assumption is a new explicit OAuth consent/reconnect because current Composio does not offer a supported usable-token export path. Owning the OAuth client can improve future portability, but does not make credentials automatically exportable or scope/redirect changes harmless. Any supported transfer needs provider agreement, compatible OAuth-client identity/scopes, a secure credential channel, user notice/consent as required, and no token exposure to the model or telemetry.
6. **Canary one app for BK, then a second user.** Display which provider/account is active and permit only benchmarked capabilities. A provider switch changes the connection revision and invalidates pending approvals and runtime sessions. Re-select the new connection per chat after reviewing scopes. Preserve old connection metadata and effect history for diagnosis, not executable old grants.
7. **Retire old accounts through verified cleanup.** Once the user accepts the replacement, disable the old connection, cancel pending not-yet-dispatched operations, purge authorization-scoped result caches, and process remote deletion through the outbox. Enumerate superseded/orphan accounts from the reconnect defect under authorized access. Track broker credential deletion, upstream grant revocation, execution-log retention, and chat-history retention separately.
8. **Rollback without replay.** Flip routing only for future operations. Never replay a completed or `unknown` write through the old provider. Check that any old account is still authorized and user-selected; if it was revoked, rollback requires a fresh consent flow. Invalidate new sessions/approvals, preserve the operation ledger, and reconcile uncertain effects before retry. Keep migrations additive until the canary and cleanup gates pass.

### Gaps

- BK must identify target apps and the original failed workflow before implementation can choose a final provider or scope profile. Gmail/Slack/GitHub are examples for designing the test, not approved priorities.
- Benchmark inputs, acceptance thresholds, regional processing/retention terms, real-send authorization, and any budget for provider/LLM calls require approval. No benchmark result is claimed in this note.
- The proposed adapter/state model is new design work. Existing `packages/integrations-composio` does not implement it, and current durable chat messages should not be mistaken for a durable approved-operation engine.
- A final migration plan needs an authorized inventory of connection/account IDs, provider grant ownership, production OAuth registrations, current grandfathered pricing, and remote-deletion behavior. Until then, immediate replacement would be speculation rather than a justified decision.
