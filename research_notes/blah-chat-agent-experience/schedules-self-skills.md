# Conversation schedules and agent-proposed skills

## 1. What exists, and how should conversation-created schedules execute safely?

### Takeaway

The repository has an unused-looking `scheduledPrompts` data model, not a working user automation feature. Reuse Convex's transactional scheduler and durable chat records, but introduce reviewed schedule intent, immutable revisions and an occurrence ledger before allowing unattended agent work. A reminder delivers previously approved text; a scheduled agent job performs fresh, bounded reasoning and therefore needs current authorization, credentials and spending checks. Evidence: [schema](../../packages/backend/convex/schema.ts#L994), [cron registrations](../../packages/backend/convex/crons.ts), [tool registry](../../packages/backend/convex/generation/tools.ts).

Primary scheduling guarantees, fetched live:

- Convex stores scheduled functions durably. `runAt` takes an absolute date/timestamp; scheduling inside a mutation is atomic with its data writes. Scheduling from an action is not atomic with the action's later success. A call can schedule at most 1,000 functions with 8 MB total arguments. [Scheduled functions](https://docs.convex.dev/scheduling/scheduled-functions)
- Scheduled mutations have exactly-once execution guarantees for committed database effects and automatic retry of internal Convex errors. Scheduled actions run at most once and do not automatically retry transient failures. These guarantees do not make a provider call or browser submission exactly once. [Error handling](https://docs.convex.dev/scheduling/scheduled-functions#error-handling)
- Scheduling does not propagate the caller's authentication. Pass trusted identity from an authorized admission and revalidate its current entitlement/access; a model-supplied `userId` is not authority. [Auth](https://docs.convex.dev/scheduling/scheduled-functions#auth)
- Canceling a pending function prevents execution. Canceling an already-running function does not stop its body, though functions it schedules will not run. Scheduled-function results remain available for seven days after completion, so that table is not long-term user run history. [Cancellation and status](https://docs.convex.dev/scheduling/scheduled-functions#canceling-scheduled-functions)
- Deployed Convex cron expressions have five fields and run in UTC. A cron job has at most one running invocation; later invocations may be skipped if the previous invocation is still executing. This does not serialize child actions or provide per-user schedule overlap policy. [Cron jobs](https://docs.convex.dev/scheduling/cron-jobs)
- Convex Workflow supports persisted steps, delayed execution, event waits, configurable action retries, reactive status and cancellation. Its README specifically says action retries default to off and cancel does not interrupt in-progress actions. Replay requires a deterministic workflow body; meaningful step changes can cause determinism violations. [Official workflow README](https://github.com/get-convex/workflow#readme)
- Existing `date-fns-tz` uses runtime `Intl` data, supports IANA-zone formatting/conversion, and returns invalid values or throws for invalid date/zone combinations depending on the API. Its documented helpers are not a recurrence parser or a documented explicit DST-fold/gap selection API. [Maintainer documentation](https://github.com/marnusw/date-fns-tz#readme)

### Inferences

Everything below is a proposed implementation contract, not existing behavior or approved defaults.

#### Separate three user intents

| User request | Stored kind | Execution contract |
| --- | --- | --- |
| "Add renew passport to my tasks, due Friday" | Existing task | Store task/deadline only. Do not claim notification delivery. |
| "Remind me Friday at 09:00 to renew it" | `reminder` | Deliver reviewed text through an enabled in-app destination. No LLM, browser or third-party action at fire time. |
| "Every Friday, research passport appointment availability and draft my options" | `agent_job` | Admit a new bounded run with approved read sources and pinned skills. Save output internally; any submission or other consequential action waits for separate fresh review. |

A scheduled time authorizes an attempt within its reviewed scope, not whatever the model later finds useful. Initial agent jobs support reading and drafting only. A request to "send this every Friday" can create a schedule draft that explicitly says delivery beyond the app is blocked pending a separately designed action policy. It must not silently reinterpret the request as permission to send.

#### Conversation tool and API contract

Suggested factories go in `packages/backend/convex/ai/tools/schedules.ts`, with trusted backend operations in new `packages/backend/convex/schedules/{crud,validation,dispatch,runs}.ts`. Keep factory-per-tool exports if that better fits surrounding code. Register in `generation/tools.ts` with explicit capability checks. These paths/functions do not exist yet.

| Proposed model-visible tool | Input and result | Authority |
| --- | --- | --- |
| `createSchedule` | Bounded title/task, kind, structured recurrence, IANA timezone, optional approved project/context selectors, proposed model policy/skill versions and limits. Returns `review_required`, schedule/revision/confirmation IDs, normalized preview and next five occurrences. | Saves an owned draft only. Does not arm execution. User/run identity is injected, never an input field. |
| `updateSchedule` | Schedule ID, `expectedRevision`, validated patch and stable request ID. Returns a new revision with before/after preview. | Material changes require renewed review. Suspend future firing while the changed revision awaits review; retain the previous revision for audit, not hidden continued execution. |
| `pauseSchedule` | Exact ID and optional reason. Returns persisted paused state and running-occurrence status. | Owner-authorized reduction of authority can happen immediately. State clearly whether a current run was also stopped. |
| `resumeSchedule` | Exact ID and expected revision. Returns review preview, current missing dependencies and next occurrence. | Never renews expired consent itself. A separate authenticated review arms the current revision. |
| `listSchedules` | Bounded status/kind filters and cursor. Returns IDs, concise task/rule/timezone, state, next run and last outcome. | Owner-only current projection. Names require disambiguation; no fuzzy mutation of the first match. |

Use a shared Zod discriminated request contract, Convex runtime validators and server-side semantic checks. Describe each tool field, cap strings/pages, and use consistent structured results such as `{status, scheduleId, revision, reviewId?, preview?, errorCode?, retryable?}`. Bound results before model continuation. Do not copy the task tool's `confirmDelete: true` pattern into execution authorization: a model can generate that boolean itself. Evidence for the factory convention and existing boolean confirmation: [taskManager.ts](../../packages/backend/convex/ai/tools/taskManager.ts), [tool guidance](../../.agents/skills/ai-tool-creation/SKILL.md).

Every draft/mutation request needs a stable owner-scoped request key and payload hash, derived from authenticated client intent or durable run/tool-call identity. A duplicate returns the same draft/revision/result; reusing a key with different content rejects. Store this deduplication transactionally. Do not cache schedule or skill mutations in the per-generation search map. Read-only list/resource caches must include owner/access scope and revision, and invalidate after changes. Preserve review IDs, version hashes and status/error codes in bounded model results; generic truncation must not corrupt an authorization reference.

Suggested public functions are `api.schedules.crud.list/get/proposeCreate/proposeUpdate/pause/revoke` plus an authenticated `confirmRevision` review mutation that the model cannot call as a tool. It verifies owner, unexpired review nonce, exact normalized payload hash and revision using compare-and-swap. Natural-language "yes" may be resolved through an authenticated user-turn handler bound to that exact card, but not accepted as an unscoped model claim. Do not depend solely on hiding the confirm function from the registry; the tool dispatcher must refuse user-review operations.

REST adapters, if needed for mobile/CLI, should map `GET/POST /api/v1/schedules`, `GET/PATCH /api/v1/schedules/:id`, `POST /:id/{confirm,pause,resume,revoke}`, and `GET /:id/runs` to the same backend authorization/validation. Use existing `formatEntity`, `formatEntityList`, `formatErrorEntity` and private/no-store middleware, not a second independent scheduler implementation. These are proposed endpoints. Existing authentication/envelope constraints are documented in [data-security.md](../blah-chat-modernization-review/data-security.md#are-payer-selection-accounting-api-contracts-and-operations-dependable).

#### Timezone and recurrence validation

Start with once-only and structured daily/weekly/monthly rules. Keep user text for display/provenance; only the normalized deterministic rule drives execution. Reuse locked `date-fns-tz@3.2.0` for zone rendering/conversion behind a tested `resolveLocalOccurrence` adapter. Do not add cron/RRULE libraries without an advanced-rule requirement. The library does not by itself settle ambiguous local times.

1. A one-off requires a valid future instant and an explicit display zone. Relative dates use a server-captured reference instant plus the user-confirmed zone, never the worker's local timezone. Ask if the zone, AM/PM, "next Friday" or start date is ambiguous. Browser zone can be a suggested value, not silent authority.
2. Recurrence stores local wall-clock fields plus an IANA zone. Compute each occurrence in that zone, then persist UTC `scheduledFor`. "09:00 every day" is not "add 24 hours to yesterday's UTC instant". A travelling user's browser timezone must not change an armed schedule.
3. Validate canonical zone acceptance, strict `HH:mm`, calendar date bounds, weekdays, month days, interval/count/until combinations, finite timestamps and end after start. Reject NaN and impossible rules. Separate elapsed-duration intervals, if later supported, from wall-clock recurrence.
4. Make DST behavior part of the reviewed policy. Proposed recurring default: skip a nonexistent local time and choose the earlier instant for a repeated time, once only. A one-off in a gap/fold asks the user to choose. Show upcoming occurrences with zone and numeric UTC offsets, including the next transition when relevant. These are proposed defaults requiring BK review.
5. Round-trip local-to-UTC-to-local to detect nonexistent times, and use an explicit candidate-resolution algorithm to detect both fold instants. A single successful round trip does not detect ambiguity. Do not assume every transition is exactly one hour or every day is 24 hours. If the adapter cannot resolve a case confidently, block that rule rather than normalize silently.
6. For "31st monthly", propose skipping months without that date; expose "last day" as a different explicit rule. Do not silently clamp to February's final day. Confirm weekday numbering in the API contract rather than inheriting JS/UI numbering by accident.
7. Bound rule expansion, preview count, time horizon, minimum interval and maximum occurrences/day. Store recurrence-engine version and record runtime/timezone-data changes when available. On runtime TZ-data updates, recompute future occurrences under the local-time contract; material preview changes should be visible. No claim is made that existing `Intl` exposes a portable timezone-database version.
8. Initially reject raw cron/RRULE with `unsupported_recurrence` and offer the supported structured equivalent. If advanced rules become required, choose **one** validated grammar/parser, document cron day-of-month/day-of-week semantics or RRULE DTSTART/TZID/UNTIL/COUNT semantics, reject unsupported extensions, and enforce bounded expansion. Never silently treat local cron as Convex's UTC cron or accept arbitrary expressions because an LLM produced them. [Convex UTC contract](https://docs.convex.dev/scheduling/cron-jobs#supported-schedules)

#### Durable dispatch, overlap and recovery

Suggested schedule lifecycle:

```text
draft -> validating -> review_required -> active
validating -> invalid -> draft
active -> paused | blocked | completed | revoked
paused | blocked -> review_required -> active
active -> review_required                 [edited revision; old callback fenced]
any nonterminal state -> revoked
```

Suggested occurrence/run lifecycle:

```text
due -> claimed -> preflight -> queued -> running -> succeeded
due -> skipped                           [misfire, overlap, expiry]
preflight -> blocked                     [consent, access, connector, quota]
running -> waiting_for_user -> queued     [fresh approved continuation]
running -> retry_wait -> preflight        [known safe transient failure]
running -> failed | needs_reconciliation
claimed | queued | running | waiting_* -> cancelling -> cancelled
```

- Arm a schedule in one mutation that stores reviewed revision/consent, calculates next occurrence and calls `ctx.scheduler.runAt(nextRunAt, internal.schedules.dispatch.fire, {scheduleId, revision, occurrenceKey})`. Store the scheduler ID. Keep one next wake-up, not thousands of pre-enqueued recurrences. Use a bounded periodic reconciliation cron as a safety net, not as proof of exact-on-the-minute delivery.
- The firing mutation compares current state/revision/epoch, deduplicates the occurrence, advances the recurrence cursor and schedules the next wake-up atomically. Reminder insertion can finish transactionally there. Agent work creates a claimed occurrence and enqueues a shared run after current preflight. A stale callback after pause/edit/revoke becomes a recorded no-op, not another job.
- Due times express desired start, not an SLA. Store `scheduledFor`, `enqueuedAt`, `startedAt` and lag separately. A skipped or blocked run remains visible. A global cutover/scheduling pause must block already-enqueued callbacks as well as cron dispatch; `CUTOVER_PAUSE_CRONS` alone cannot promise that.
- Revalidate owner existence/enabled state, current schedule consent/expiry, project/conversation ACL, selected input accessibility, pinned skill publication/revocation, current allowed model/provider/payer, connector state/scopes, concurrency and budget **at occurrence admission and before each tool/effect**. A background function receives trusted identity from the durable record, not a user session or a stored JWT.
- A valid connector at creation is not valid forever. Refresh authentication only through the connector's existing approved lifecycle; do not broaden scopes or reconnect by injecting credentials. A new account linked to the same provider must not silently replace the approved connection identity. Missing/revoked/expired credentials produce `blocked`, pause the schedule and notify once.
- Proposed default overlap is `skip_new` while an earlier occurrence is running or awaiting a user. Record `skipped_overlap`. A later opt-in `queue_latest` keeps at most one coalesced pending occurrence. No unbounded queue and no parallel use of the same writable computer. Platform cron serialization does not replace this per-schedule transaction/lease.
- Proposed agent-job misfire default is `skip`, recording the missed range/count and scheduling the next future slot. Reminders may offer `latest_once_within_grace`. A user-requested catch-up is a new reviewed bounded run. Resume never replays every missed occurrence, and revocation/consent expiry never counts as catch-up permission.
- Safe transient reads/model preparation can retry with bounded exponential backoff/jitter, deadline, maximum attempts and the same logical run. Re-run current authorization and reserve remaining budget before each attempt. Do not blindly replay a whole tool-using generation after a late failure. Preserve succeeded tool outcomes and resume from a durable checkpoint.
- Persist an operation intent before external dispatch. When acknowledgement is lost after a potential external effect, enter `needs_reconciliation`; do not label it harmless failure and retry. Provider-supported idempotency keys help only for that provider operation. GUI clicks have no universal exactly-once guarantee. This remains necessary even if Workflow orchestrates the run. [Scheduler error semantics](https://docs.convex.dev/scheduling/scheduled-functions#error-handling), [Workflow cancellation/retry contract](https://github.com/get-convex/workflow#readme)
- A reconciler pages indexed due/expired-lease/blocked-delivery rows, repairs missing wake-ups, fences stale attempts, settles known usage and retries safe notification writes. It does not restart an uncertain external action. Repeated failures trigger a configurable circuit breaker and owner-visible paused reason. Keep the original error, last successful checkpoint and explicit Retry/Review/Disable actions.
- Distinguish Pause future runs, Stop this run and Revoke schedule. Revoke increments an authorization epoch, cancels pending wake-ups, denies new tool dispatch, invalidates approvals and requests running workers to stop. Canceling Convex work alone cannot halt an in-flight request. Show uncertain/already-completed effects honestly.

#### Current consent, hard limits and offline/browser-absent behavior

Execution is an intersection, evaluated server-side:

```text
current platform policy
  intersect current owner entitlement and quota
  intersect reviewed schedule revision and unexpired read/draft consent
  intersect current connector/input ACL
  intersect published pinned skill restrictions
  intersect actual selected model/runner capabilities
```

Fresh action approval, if such actions are later supported, must additionally bind exact action/data/destination/observation, owner and expiry. Permission to recur is not an action approval. Expired approval pauses/blocks the run and asks again. There is no hidden `autoApprove`, "approved because scheduled", model-authored approval token, or fallback to a more permissive tool.

Existing active-connection discovery can return up to 100 tools, and wrappers currently invoke them without a durable run-policy gate. A schedule must not simply inherit `buildToolsAsync`'s full integration set or the ordinary write tools. Start from an explicit server-mapped read-only allowlist and recheck on execution. Unknown action semantics are denied. Evidence: [Composio discovery/wrapper](../../packages/backend/convex/composio/tools.ts#L59), [integration assembly](../../packages/backend/convex/generation/tools.ts#L280).

Authorize canonical tool/action IDs and schema/policy versions before provider name normalization, then retain the exact canonical-to-model-name mapping on the run. A normalized tool name, provider prefix or tool description is not sufficient evidence that an action is read-only. Connector tool/schema changes require compatibility validation; adding a newly available action never expands an existing schedule consent.

Reserve and enforce per-run model tokens/dollars, steps, tool calls, wall time, search/network cost, output bytes and any compute runtime. Also enforce owner daily/monthly automation spend, concurrent active runs, schedule count and recurrence frequency. Budgets include retries, auxiliary parsing/skill-drafting calls, cancelled/failed billable calls and reservation settlement. Existing awareness-only `budgetTracker` and recorded-spend checks are insufficient hard limits; `Promise.race` timeouts do not stop underlying work. [budgetTracker.ts:1-10,120-144](../../packages/backend/convex/lib/budgetTracker.ts#L1), [chat.ts:144-157](../../packages/backend/convex/chat.ts#L144)

Safe defaults when nobody is watching:

- Text-only reminders and read/draft jobs run server-side without a browser tab. Save results durably; a toast is not delivery.
- No interactive host browser, user's computer, saved login or live viewer is presumed. A required human login/2FA/browser handoff yields `waiting_for_user` or `blocked`; do not bypass it with API credentials or a different execution method.
- A skill that requires a computer cannot silently allocate/resume one merely because the schedule fired. An explicitly reviewed compute policy and available compatible runtime are prerequisites. Initial schedules can exclude computer capability entirely. If later enabled, use a clean run-owned environment, pinned template, explicit network/input policy and hard compute reservation from [computer-skills.md](../blah-chat-modernization-review/computer-skills.md#2-how-should-a-conversation-owned-computer-work-safely-and-durably).
- Do not leave a VM/model request running while awaiting review. Persist checkpoint and release/pause resources under the approved retention policy. Re-observe and revalidate on resume. Existing message cleanup must recognize that a waiting run is not a ten-minute generation timeout.
- A scheduled job cannot arm other schedules, publish skills, broaden its own tool policy or amend its reviewed task. It can return a proposed draft/change for a later interactive user review, under explicit proposal limits.

### Gaps

- No deployed `scheduledPrompts` rows or user behavior were inspected. Absence of an audited runner is a code-search finding, not proof that no separate deployment or historical implementation ever existed.
- BK must decide recurrence scope, default timezone source, DST/month-day/misfire/overlap policies, schedule/approval expiration, notification channels, job-output destination, retry/circuit-breaker settings, numerical quotas and retention. The defaults above are conservative proposals.
- `date-fns-tz` documents conversions, not all ambiguity-selection guarantees needed here. Implement and test the adapter before choosing a different timezone library. No raw cron/RRULE parser is selected because advanced syntax is not necessary for the first feature.
- Workflow is a credible future runner for approval waits, not a prerequisite for reminders or a selected installed dependency. If chosen, verify/pin the then-current package and Convex compatibility in a scoped task; keep action authorization/idempotency outside assumptions about framework durability.

## 2. How can the agent create useful skills without silently rewriting itself?

### Takeaway

Give the agent a tool to propose a versioned, tenant-owned skill draft from selected conversation context. Publication and expanded execution permissions should require explicit user review by default, pending BK's decision. The agent can reuse approved skills; it cannot promote its own draft into system policy or create its own approval. This extends the private versioned library already proposed in [computer-skills.md](../blah-chat-modernization-review/computer-skills.md#3-how-should-user-added-skills-be-imported-selected-and-executed).

### Cited findings

- Agent Skills defines a directory with `SKILL.md`, YAML frontmatter and Markdown body. `name` and `description` are required; scripts/references/assets are optional conventions. Names are 1-64 characters with lowercase alphanumeric/hyphen constraints; descriptions are 1-1024 characters; optional compatibility is at most 500 characters. `allowed-tools` is experimental and client-dependent, not a portable authorization service. [Specification](https://agentskills.io/specification)
- The specification recommends progressive metadata/instructions/resource loading, a main file under 500 lines and instructions under roughly 5,000 tokens. These are recommended content sizes, not guarantees that arbitrary packages are safe. [Progressive disclosure](https://agentskills.io/specification#progressive-disclosure)
- The official integration guide supports hosted discovery APIs/upload provisioning, a dedicated activation tool, user-explicit invocation, filtering disabled/inaccessible skills, deduplicating activations and protecting skill instructions through compaction. It also documents deliberately lenient parsing, while the specification defines strict format constraints. A hosted multi-tenant validation boundary may intentionally be stricter. [Integration guide](https://agentskills.io/integrate-skills)
- The earlier local audit found developer `.agents/skills` guidance but no production tenant skill catalog/activation tables in the schema or tool registry. That is distinct from existing custom instructions, project prompts and memory. [computer-skills.md current map](../blah-chat-modernization-review/computer-skills.md#current-repository-map), [generation/tools.ts](../../packages/backend/convex/generation/tools.ts), [systemBuilder.ts:147-159](../../packages/backend/convex/lib/prompts/systemBuilder.ts#L147)
- Existing tool results are universally converted into a `<tool-data>` string telling the model they are not instructions. Skill activation needs a deliberately typed subordinate-instructions representation, not a silent exception that promotes arbitrary tool text into system authority. [generation/tools.ts:304-354](../../packages/backend/convex/generation/tools.ts#L304)
- Existing compaction summarizes message content from chronological history, slices the first 16,000 characters and does not carry normalized tool records. A generic conversation summary cannot be trusted as the sole source of skill instructions, authorizations or source provenance. [conversations/compact.ts:64-95](../../packages/backend/convex/conversations/compact.ts#L64), [context-caching findings](../blah-chat-modernization-review/context-caching.md#what-exists-and-can-its-context-measurements-safely-trigger-automatic-compaction)

Guidance loaded for design, not to create global skills: `skill-creator` recommends capturing intent, drafting, representative positive/negative cases, user review and revision; `writing-for-agents` recommends bounded descriptions, checkable completion criteria and on-demand references. Those are design influences, not claims that blah.chat implements those workflows. Agent Skills remains the public packaging source above.

### Inferences

#### Definition and scope

A reusable skill encodes a repeatable procedure with a trigger, inputs, steps, output contract, completion checks and known limitations. A one-off answer, private fact, current browser state, saved password or task-specific report is not automatically a skill. Prefer an artifact/template or ordinary memory for those cases. Example: "Use these five source checks whenever preparing my weekly research brief" is reusable; "This week's five findings" is an output.

The product should say "Save this approach as a skill?" rather than claim the model has trained itself. This is managed workflow memory, not changed model weights, privileged self-modification or edits to the app's system prompt.

Proposed default flow:

```text
user asks to capture approach OR agent offers a non-persistent suggestion
  -> selected source context + intent clarification
  -> proposeSkill writes private draft
  -> bounded validation + extraction/compatibility diagnostics
  -> review_required
  -> user edits/tests/reviews exact version
  -> user publishes immutable version
  -> explicit invocation or separately enabled automatic discovery
```

No implicit background harvesting of every conversation. Agent-initiated suggestions should be quiet and dismissible, with no draft persisted until the user requests saving or an explicitly enabled draft-proposal policy exists. BK's request for self-created skills does not settle that policy.

#### Proposed tools and owner APIs

Add `proposeSkill` and `reviseSkillDraft` to the conversation tool registry under non-incognito write policy. The first accepts a bounded desired name/description, reusable workflow, declared inputs/output, completion checks, references and selected source-message/artifact IDs. The second accepts draft ID, expected revision and a bounded change. Neither accepts `userId`, arbitrary storage paths, raw credentials, permission grants or a publish boolean.

These tools save draft packages and return structured `{status: "review_required"|"invalid", skillId, draftVersionId, reviewId, summary, validationIssues, requestedCapabilities, previewRef}`. Full content is fetched through an authorized review view, not copied into every tool event. Optionally provide a bounded `getSkillDraft` for the model to refine its own user-requested draft. Updating an existing published skill always creates a new draft version.

Suggested operations in new `packages/backend/convex/skills/{drafts,validation,versions,activation}.ts`:

- `proposeFromConversation` and `reviseDraft` share trusted internal helpers with model tools, checking owner/run policy and source access.
- `validateDraft` runs deterministic structural/security checks without executing scripts or calling a model.
- `publishVersion` is an authenticated user-review mutation, compares the exact draft/package hash and current validation result, then publishes once. The model tool dispatcher has no path to approve it.
- `list`, `getVersion`, `diffVersions`, `disable`, `revokeVersion` and `setPublishedVersion` implement owner-scoped library/history controls. Rollback selects a still-valid published immutable version; it does not rewrite old bytes or revive revoked permissions.
- Existing proposed `activateSkill`, `readSkillResource` and separately privileged `runSkillScript` remain the use path. Creation/publishing is not execution permission. Reuse a single skill validator/import boundary for uploaded and self-generated packages.

Keep any skill-authoring LLM prompt in a new dedicated module under `packages/backend/convex/lib/prompts/`, use centralized model definitions, bounded input/output and attributable per-call cost. No model is needed for deterministic create/validate/publish operations. If an additional authoring/evaluation model is invoked, treat it as a budgeted explicit operation, not an invisible free side call.

#### Extend the versioned library rather than add a second skill store

Reuse the earlier proposed `skills`, `skillVersions`, `skillVersionFiles`, `skillBindings` and `runSkillActivations`. They do not yet exist in the production schema. Add these fields/contracts to that proposal:

| Record | Additional proposed data |
| --- | --- |
| `skillVersions` | `origin: conversation_generated|user_authored|imported`, parent version ID, draft revision, `createdByUserId`, generating run/tool-call ID, author model/config/prompt version, source-manifest hash, validation-policy version, risk/compatibility summary, immutable package hash, review/publish actor/time. A model's claimed author/version metadata is never authoritative. |
| `skillDraftSources` | Draft-version to selected conversation/message/artifact junction; branch head/content revision/hash, purpose and permission snapshot. Store minimum references/excerpts under the owner's retention policy, not an automatic permanent transcript copy. |
| `skillReviews` | Owner, exact draft/package hash, validation report hash, proposed activation scope/mode, declared script/network/data requirements, expiring review nonce and accepted/rejected/replaced state. Publication consent remains separate from execution capability grants. |
| `skillValidationReports` | Version/draft hash, validator/scanner versions, structural/path/size findings, secret/private-context warnings, compatibility and executable inventory. A report applies only to those exact bytes. |
| `skillEvaluationCases` | Optional version-bound safe input fixtures, expected completion properties and positive/negative trigger cases. Test data is owned and separately authorized; no copied live secrets or production writes. |

Keep package files immutable after publication. Save edits to a new version, render a meaningful instruction/file/requirements diff, and revalidate. Limit unpublished drafts per owner, creation frequency, per-run proposal count and retained storage so a self-improvement loop cannot fill storage or repeatedly call an authoring model.

#### Validate content, filesystem and execution separately

1. Enforce strict safe YAML parsing with duplicate-key/alias/depth bounds, required metadata and the public format constraints. Use a documented ASCII slug policy initially because the specification mixes "unicode lowercase alphanumeric" wording with `a-z`/`0-9` examples. Show diagnostics rather than silently renaming or repairing content into different bytes.
2. Suggested starting policy for generated text drafts is a 5,000-token main-body target, 500-line main-file target, 1 MiB hard text-file cap, 10 MiB total draft package, 100 files and bounded directory depth. These are proposed product limits, not standard/provider limits. Short descriptions still have to meet the 1,024-character spec cap. Enforce aggregate owner storage and an activation-time model context cap independently.
3. Model-provided paths must be canonical relative manifest members within a virtual skill root. Reject absolute/drive/UNC paths, traversal, NUL/control characters, duplicate/case/normalization collisions, links and special files. Model tools cannot write `.agents`, `.claude`, host home directories, `AGENTS.md`, deployment files, system prompts, hooks or connector configuration. A tenant package is stored through owned blobs, not arbitrary filesystem writes.
4. Default self-created skills to instructions and references only. If scripts are later enabled, every file is visible in review with its hash, interpreter, dependencies, input/output contract and requested network/data behavior. Validate without executing. No install/postinstall/import hook runs during generation, validation or publication.
5. A generated script can be harmful or wrong even if authored by the agent. Run only the approved immutable file under the existing proposed isolated script gateway, no secrets/browser cookies/host mounts/network by default, bounded CPU/time/output, approved prebuilt dependencies and safe structured arguments. Publishing a file is not permission to execute it. [Script boundary proposal](../blah-chat-modernization-review/computer-skills.md#secure-skill-script-execution-in-e2b)
6. Parse `allowed-tools` and compatibility as requested constraints/diagnostics. The effective tool set is the intersection of current platform/user/run capabilities and any skill restriction. A skill cannot add tools, approve actions, change the model policy, grant network/secret access or turn off confirmation. Unsupported dependencies produce a visible blocked reason, not an improvised shell or privileged fallback.
7. Render preview Markdown/links safely. Prompt injection can reside in the description as well as body/resources. Secret scanning, malware checks and a model critique are defenses, not proof of safe behavior. Critical boundaries remain deterministic authorization at read/execute/publish.

#### Extract procedure without retaining private context

- User chooses the conversation branch/source turns or the app proposes a narrow selection for review. Resolve source IDs through current ACLs and content revisions; do not feed inactive branches, collaborators' private resources or unrelated memory retrieval into the authoring prompt. A summary alone is not enough evidence of source selection.
- Default extraction replaces names, emails, account IDs, confidential examples, internal URLs, client/customer facts and specific file contents with typed placeholders. Preserve the reusable decision/process, not a transcript recap. Show "Included from this conversation" and "Replaced with placeholders" beside the preview.
- Never store passwords, keys, session cookies, OAuth state, raw access tokens, secret-bearing URLs, connector response dumps, hidden system instructions or private browser screenshots as skill resources. References to a connection use an owned logical selector resolved at execution, never a token. If a credential-looking value appears, block publication pending removal rather than merely obscuring it in the UI.
- Distinguish private but intentionally necessary procedure context from secrets. If an owner explicitly wants a confidential company-specific reference, keep it private, selected, ACL-bound and clearly flagged. Do not turn "private library" into permission to retain every source indefinitely or cross-share it.
- Collaborative conversations need a policy decision. Initial proposal is owner-only skill capture from that owner's authorized material; if provenance includes another participant's content, require agreed sharing/capture rules or block. Do not publish private draft bodies into the shared assistant transcript.
- Incognito cannot silently create a durable skill or schedule. A later explicit "save outside incognito" transfer would need its own source preview/consent and retention change; leave it unsupported initially.
- Source deletion must not leave hidden copied excerpts in drafts, telemetry or caches. Explain when a separately published skill is an intentional retained copy, provide deletion controls, and propagate deletion to source manifests according to policy. Published provenance can retain minimal hashes/timestamps without retaining private source text forever.

#### Version lifecycle, activation and revocation

```text
draft -> validating -> review_required -> published
validating -> rejected -> draft_revision
review_required -> draft_revision        [edits invalidate review]
published -> superseded | disabled | revoked
published_version_A -> selected_as_current [rollback, if still valid]
```

`superseded` means a newer version exists, not unsafe. Existing runs/schedules remain pinned until an explicit reviewed upgrade. `disabled` removes new discovery/activation under its scope. `revoked` denies new activation/resource/script dispatch and blocks dependent scheduled runs; fence running execution at the next gateway check. Neither revocation nor rollback undoes completed external effects.

Initial publication default should be explicit-only. The owner can separately enable automatic discovery and user/project/conversation scope. The agent may automatically activate an eligible published version within the current run's policy, but must not automatically publish a draft or widen scope because it believes the draft is useful. This is the main unresolved BK product question, not a standards requirement.

For a first skill, offer two or three representative positive cases plus a near-match that should not activate. Validate structural properties with fake tools first. Any live model/compute test consumes an explicit budget, and any external effect remains blocked. An optional test run must not send messages, modify records or use real credentials merely to prove the skill works.

### Gaps

- BK needs to confirm whether the agent can persist unsolicited drafts at all, whether publication always needs review, automatic-discovery defaults, sharing/collaborator rules, permitted scripts/dependencies, numerical size/storage limits and retained-source policy. Proposed default is private text-only drafts, explicit publish review and explicit-only initial use.
- The public format supplies packaging/disclosure conventions, not a tenant ACL, secrets classifier, script sandbox, evaluation guarantee or permission standard. Those are application responsibilities.
- No existing production `skills` table or skill-create UI was found in the audited paths. Developer-agent skill directories are not a product user's library and must not be copied/imported automatically.

## 3. How should schedules, skills, context and the user journey fit together?

### Takeaway

Use one durable run/approval system and one request-context planner for interactive and scheduled work. Keep schedule review and skill publication visible as small actionable cards, preserve their exact versioned provenance outside summaries, and make failure/revocation states recoverable without replaying external effects. Existing generation and context defects are prerequisites to fix, not guarantees inherited by the new features. [Generation audit](../blah-chat-modernization-review/generation.md), [context audit](../blah-chat-modernization-review/context-caching.md).

### Cited findings

- Generation persists partial assistant content and normalized tool calls/results, but the current tool loop runs inside a scheduled action rather than a durable checkpoint engine. Main generation uses a 15-step tool limit. ### Inferences

#### Versioned context and bounded loading

1. Every interactive or scheduled run gets an immutable provenance manifest: initiating owner/source, conversation branch/context revision, schedule version/occurrence/consent, activated skill version/file hashes, approved connector/tool IDs, model-policy/config/prompt versions, actual chosen provider/model/payer, runner version, effective policy hash and budget reservation. Dynamic runtime authorization is rechecked even when the pinned manifest still matches.
2. A scheduled job should use reviewed task instructions plus selected durable inputs, not append the entire ongoing conversation every week. Proposed default output is an owner-only per-occurrence conversation linked from the schedule. An optional dedicated automation thread must use branch-aware context and cannot silently read a changing collaborative chat or interrupt an active interactive generation.
3. At each occurrence, resolve enabled **approved** skill versions and build a small deterministic metadata catalog. For required pinned skills, load those exact versions directly; do not let automatic discovery substitute a similarly named draft or a new version. Read references on demand by manifest member. No eagerly loading all tenant skill bodies or arbitrary URLs.
4. A tentative context-policy starting point is a catalog capped near 2,000 tokens, at most three active skills and a total skill-body allowance of `min(10,000 tokens, 15% of usable input)`. These are experiment defaults, not approved limits. Explicit user selection that does not fit should ask for a narrower selection or compatible model, not silently drop required steps. Context limits also include tools, history, selected inputs, output/reasoning reserve and tool growth.
5. Integrate with the proposed server-owned `ContextPlan` and `prepareStep` request preflight. Preserve full native structured tool results in durable storage and return bounded model-facing extracts/references before the next provider call. Review cards carry IDs/status/preview metadata, not enormous package bodies or source transcripts. [Context planner proposal](../blah-chat-modernization-review/context-caching.md#proposal-a-one-exact-request-plan-and-a-clear-denominator)
6. Skill activation needs a typed representation of user-approved workflow guidance subordinate to platform policy. Ordinary retrieved resources remain untrusted data. Do not make the current `<tool-data>` warning and "follow this skill" instruction contradict each other, and do not use a higher-priority system message to grant uploaded content authority.
7. Compaction preserves run/schedule/approval/skill IDs and exact hashes in a durable checkpoint. Reload exact pinned instructions/resources when needed; a free-form recap must not rewrite their meaning or claim a prior action succeeded. Preserve unsettled tool-call/result pairs and pending user decisions. Deduplicate activation only while the identical content remains present in the current context epoch.
8. Keep a stable prefix ordered by base policy, stable allowed tools, approved catalog/pinned skill content and stable context checkpoint. Put per-occurrence time/status/progress in the volatile suffix. Cache by owner/access scope, model/API/credential version, prompt/tool/policy/catalog/skill hashes and context epoch. Never reuse another tenant's private result or an unqualified cached prompt by slug alone. Revocation/access changes invalidate affected cache use immediately; warm cache never overrides current policy.
9. Multi-hour/daily schedule intervals should not be assumed to hit provider caches. Do not purchase extended cache retention merely for potential automation savings. Distinguish application prompt assembly cache, action-local search cache and provider KV cache. Measure per-request cache read/write usage and price the real model/hosting path before claiming savings. [Caching contract proposals](../blah-chat-modernization-review/context-caching.md#proposal-d-stable-prefix-and-cache-policy)
10. Model switching or fallback revalidates tool/media/context/privacy and price constraints. Required scripts/computer tools need a compatible allowed model/runner; a text-only model cannot execute a nonexistent tool. Missing credentials or an unavailable model pauses with alternatives rather than silently spending through platform keys or choosing a more expensive/more permissive provider. New skill versions may tighten requirements and therefore need reviewed schedule upgrades.

#### Calm conversational journey

Use existing chat tool-card conventions and the notification inbox, but back every decision with an owned durable record. The following copy/UI is proposed.

| Moment | Chat card | Detail and action |
| --- | --- | --- |
| Ambiguous request | "What time should this run?" | A compact question with timezone/time choices, bound to a draft ID. User can answer inline or in the composer. No blocking browser dialog. |
| Schedule proposal | "Every Friday at 09:00, Europe/London" | Kind, exact task, next five times/offsets, selected data/skills/model, spending ceiling, consent expiry, and "Read and draft only". Actions: **Create schedule**, Edit, Cancel. No claim that it is active before confirmation. |
| Schedule active | "Scheduled. Next run Friday at 09:00." | Quiet persistent chip with View/Pause. A later update shows a diff and explicitly says future runs are paused until review. |
| Execution | "Preparing inputs..." then "Drafting your brief..." | One live progress row with run link and Stop. Details show meaningful steps, limits and last progress, not every internal token/tool event. Refresh observes the same run. |
| User needed | "Paused. Reconnect your calendar to continue." | Reason, latest safe checkpoint, what will happen next, and Review/Reconnect/Disable. Approval expiry never appears as a successful run. |
| Consequential action requested | "Your draft is ready. Sending needs your review." | Save output and stop at the boundary. If fresh action approvals later exist, show exact recipient/data/effect and Approve once/Reject with expiry. Schedule creation never replaces this step. |
| Completion | "Brief ready" | Output/artifact link, actual or estimated spend, run time and used skill versions. Notify once in app; do not scatter routine success toasts through unrelated chats. |
| Failure/missed run | "Didn't run: approval expired" or "Skipped: previous run still waiting" | Distinguish failure, blocked, skipped and uncertain effects. Offer the relevant safe action, not a generic retry that replays everything. |
| Skill proposal | "Save this approach as a skill?" | Show reusable purpose, when it triggers, source selection and exclusions. This suggestion alone writes nothing. |
| Skill review | "Weekly brief, draft v1" | Readable instructions/file preview, original-source references, private-data warnings, required tools/scripts and compatibility, optional safe test cases. Actions: **Publish skill**, Edit, Discard. Publication default is explicit-only. |
| Skill ready/update | "Saved skill v1" or "Review skill v2 changes" | Use now, enable automatic discovery, scope settings and version diff/rollback. No auto-enabling new execution capabilities. |

Add a Schedules management page with active/paused/needs-attention filters, next due time in its pinned zone, last result, limits, owner and Pause/Revoke controls. Schedule details show consent/dependencies, version history and paginated occurrences including skipped runs. Add a Skills library with drafts/published/disabled filters, provenance, version diff, compatibility, scope and revocation. Mobile/CLI must have equivalent review/stop/state commands without depending on a web viewer.

Extend `notifications.create`, both notification schemas and `NotificationBell` with typed `scheduleId`, `occurrenceId`, `agentRunId`, `skillId` and `reviewId` destinations as needed. Route using allowlisted application IDs, not arbitrary model URLs. Deduplicate on logical event, keep content generic enough for private inbox previews, and make read/dismiss independent of job cancellation. Existing 30-day cleanup is notification retention, not permission to delete run history or a promise of long-term run audit. [Current retention](../../packages/backend/convex/notifications.ts#L130)

Completion and notification delivery have separate retry states. A failed notification retries only delivery of the already-saved output; it never re-runs research, republishes a skill or repeats tool effects. Likewise, opening a run-history entry must not restart its job.

Question cards and approval cards are different. Clarification supplies missing task data; approval grants bounded authority to an exact pending change/action. Both need refresh-safe IDs and response state, but answering a scheduling question must not automatically approve publishing a skill or sending an external message.

### Gaps

- Numerical limits, expected schedule volume, user notification preferences, existing production run frequency/latency/cost, provider availability and hosted runtime quotas were not measured. Do not claim scalability, savings or minute-accurate execution from this audit.
- Exact durable-run engine choice remains open. Native transactional scheduling is sufficient for reminder delivery; human waits and tool retries require persisted checkpoints or an adopted workflow component. Neither choice grants exactly-once external effects.
- Approval persistence, source retention, collaborative ownership, output-thread behavior and whether any authenticated computer use is permitted are product/security decisions. This proposal does not infer them from "automation" or "create skills for itself".
- No external mutation, deployment validation, paid call, dependency installation, implementation or heavy check was authorized or performed. The implementation sequence is a proposed handoff, not a report of completed features.
