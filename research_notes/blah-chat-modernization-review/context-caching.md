# Context compaction and provider prompt caching

## What exists, and can its context measurements safely trigger automatic compaction?

### Takeaway

Compaction already exists. An opt-in browser effect starts it at 75%, but the displayed percentage does not describe the provider's actual next request. Repair context selection, accounting and summary fidelity before making automatic compaction the default. BK's request for "like 80% context usage or something" is an approximate product direction, not approval of an exact threshold or a provider-specific implementation.

Provider caching is not absent merely because no explicit options appear. OpenAI and Gemini offer implicit caching. What is absent in the inspected chat path is deliberate provider-cache policy and reliable cache observability. [OpenAI caching](https://platform.openai.com/docs/guides/prompt-caching), [Gemini caching](https://ai.google.dev/gemini-api/docs/caching), [generation.ts:648-653](../../packages/backend/convex/generation.ts#L648-L653).

Three distinct local caches must not be sold as provider KV-cache optimization:

- `conversation.cachedSystemPrompt` is a serialized **application prompt-building cache**. Generation reads it without checking a version/model/user-preference identity. Backend search found schema fields, readers and test fixtures, but no production writer. Do not claim it currently saves model prefill or assume it is reliably populated. [generation.ts:505-565](../../packages/backend/convex/generation.ts#L505-L565), [schema.ts:175](../../packages/backend/convex/schema.ts#L175).
- Download and search maps last only for one action. They avoid duplicate downloads/search execution, not repeated transformer prefill. [generation.ts:593-600,661-662](../../packages/backend/convex/generation.ts#L593-L662).
- Dexie is the browser's local data/render synchronization cache. Its refresh/offline benefits are separate from provider prompt-cache reads, cache writes and TTL billing. [useCacheSync.ts](../../apps/web/src/hooks/useCacheSync.ts), [messageTree.ts](../../apps/web/src/lib/cache/messageTree.ts).

### Inferences

- Changing `75` to `80` would preserve the wrong denominator, branch leakage and browser-only execution. Ship a server-authoritative request planner first; then choose a threshold based on its measurements.
- Automatic compaction should change the **active context representation**, not force navigation or delete visible transcript history. Preserve the manual "continue in a new chat" option as an explicit separate action.
- The fixed 30-message cutoff is itself a context-retention policy. Replace it with summary coverage plus a token-budgeted recent tail, or explicitly disclose any remaining cutoff. Raising the cutoff alone risks oversized requests.

### Gaps

- No production cache-hit rate, real context-overflow frequency, prompt sizes, tool-output sizes, summarization latency, cost baseline or preference adoption was measured. The risks above follow code paths, not incident counts.
- Deployed model limits and DB/static catalog alignment were not verified. Unknown model limits must not be treated as a confirmed 128K capacity solely because the helper provides a fallback.
- Whether compaction should be on by default, how much transcript detail BK wants retained verbatim, and whether collaborators may compact shared branches need product decisions. Current owner-only compaction authorization is not a complete collaboration policy.

## What do current provider APIs and the pinned AI SDK actually support?

### Takeaway

Use portable application summaries as the baseline for multi-model chat, with provider-native compaction as a capability-gated experiment. Cache matching and pricing are model-, API- and hosting-path-specific. Current documentation is ahead of this repository's locked SDK; do not copy current options into `any` and assume the older adapter forwards them.

### Inferences

- Native compaction may preserve provider-specific reasoning better and avoid a separate application summarization prompt, but adds provider coupling, usage/stream handling and artifact replay requirements. It is not a drop-in replacement for `compact.ts` in an app whose defining feature is mid-chat model switching.
- Cache-compatible structure is worth doing even before explicit provider controls. Enabling extended TTL or paid writes should follow measured reuse patterns and privacy approval, not a blanket "cache everything" policy.
- A cache hit lowers prefill cost and often latency; it does **not** expand the context window, make oversized attachments fit, guarantee response reuse or replace context admission.

### Gaps

- Google's full legacy caching guide redirected to the Interactions view even with the generate-content query. Search-indexed primary text says explicit TTL defaults to one hour, but the fetched full view did not reconfirm it. The API verifies configurable expiry and an official 300-second example. Set TTL explicitly in a spike; do not bake an unverified default, universal explicit minimum or implicit TTL into policy.
- No primary general Gemini text-chat compaction contract was verified. Live API sliding-window compression is a separate real-time/session feature, not evidence for normal chat summarization.
- Exact provider-native compaction model-pair replay compatibility, OpenAI compaction pricing, all hosting-path minima, Gateway pass-through for new beta fields, and ZDR eligibility for the actual deployed models/accounts require capability and policy checks. No guarantees for these are asserted here.
- Current docs/API shapes have changed between AI SDK 6 and 7. A dependency upgrade requires a scoped migration review, not a field-name substitution. No package upgrade is proposed as a prerequisite for fixing portable context accounting.

## What implementation contracts and experiments should follow?

### Takeaway

Proposal: create one server-owned context plan for every provider request, compact an older branch prefix when it approaches **roughly 80% of usable input**, preserve recent turns verbatim, and make stable prefixes independently cacheable. Keep the immutable transcript as truth; summaries and provider-native artifacts are replaceable context representations with provenance, not edits to what the user said.

### Cited findings

The following evidence motivates the contracts below; the contracts themselves are proposals, not existing behavior:

- Base prompt builds a fresh ISO datetime near its beginning; per-request rebuilding changes an early prefix. Identity/contextual memories precede project/conversation instructions; dynamic connected-app names and optional sections also change the prefix. ### Inferences

#### Proposal A: one exact request plan and a clear denominator

Add a shared backend `planContext` contract, consumed by ordinary send, regeneration, comparison, branch merge, model switch, CLI and every tool-loop provider step:

```ts
type ContextPlan = {
  conversationId: string;
  branchHeadId: string;
  transcriptRevision: string;
  contextEpoch: string;
  modelId: string;
  modelConfigVersion: string;
  gateway: string;
  host?: string;
  apiKind: string;
  promptVersion: string;
  toolManifestHash: string;
  messages: ProviderReadyMessage[];
  tools: ProviderReadyTool[];
  inputTokens: number;
  countMethod: "provider" | "local-tokenizer" | "estimate";
  countConfidence: "high" | "bounded-estimate";
  outputReserve: number;
  safetyReserve: number;
  toolGrowthReserve: number;
  usableInput: number;
  usableInputRatio: number;
  coveredMessageIds: string[];
  retainedMessageIds: string[];
};
```

The illustrative types are not a requested schema migration. Keep existing central model/prompt modules authoritative; extend their metadata instead of hardcoding provider/model IDs in UI or generation.

1. Resolve actual model, API and allowed capabilities before final admission. Construct the exact target representation, including summary, role/format overhead, full system instructions once, selected tool schemas and structured-output schema, attachment transformations, retained tool/reasoning artifacts and the pending user turn. Count the model-facing request, not raw DB rows, JSON/base64 length or lifetime usage.
2. Define `C` as the provider's combined context capacity where applicable, `Imax` as a separate maximum-input cap if specified, `O` as the chosen bounded output allocation, including reasoning where the provider shares that budget, and `S` as model/estimator-specific uncertainty and hidden-format reserve. Define `U = max(0, min(Imax, C - O) - S)`. If only a separate input limit applies, encode that model contract rather than mechanically subtracting output twice. Set actual request output limits consistently with `O`.
3. Proposed trigger: `inputTokens / U >= theta`, starting with `theta ≈ 0.8`, **or** `inputTokens + predictedNextToolGrowth > U`. The second condition handles a 70%-full prompt followed by a huge tool result. Actual hard guard is `inputTokens <= U`; it applies even if automatic compaction is disabled. Cache-read tokens occupy input just like uncached tokens.
4. Start with a conservative calibrated reserve, not an invented "exact" image count. Expose estimator method and uncertainty. Native counters should receive matching tools/system/multimodal inputs where supported, with deadlines and fallback bounds; do not add a remote token-count call to every short turn. Cache counts by content hash, tokenizer/model version, tool manifest and media resolution. Reconcile estimates against observed request counts without mixing billing totals into occupancy.
5. Preflight must happen after target-specific serialization and tools are known, before `streamText`/`generateText`. Also preflight continuations and retries. Use `prepareStep` or an explicit bounded tool loop before each subsequent provider request, never after the model has already consumed an oversized result.
6. Replace the 30-message raw tail policy with `checkpoint + unsummarized ancestry + recent atomic groups`, selected by token budget. A checkpoint's covered prefix and retained tail must partition history exactly once. If the initial turn alone, non-removable instructions or mandatory media exceed `U`, fail helpfully before a paid inference. Offer selecting pages/regions, retrieval/chunking or an eligible larger-context model. Do not silently summarize the user's only new request or silently discard attachment contents.

Illustration only: for a combined 128K context, chosen 8K output reserve and 4K uncertainty reserve, `U=116K`, so an 80% trigger is 92.8K input, not 102.4K. Add predicted tool growth to decide whether to act sooner. Real values must come from model capability metadata and measurements.

#### Proposal B: branch-aware durable compaction

- Introduce an immutable context checkpoint and a durable operation record, separate from assistant prose. Record owner/access scope, source conversation, branch ancestry hash, covered start/end and explicit message IDs or verifiable range manifest, source revisions/content hashes, previous checkpoint, retained-tail boundary, attachment/tool-result references and their versions, summary prompt/schema version, authoring model/provider, target compatibility, token counts/method, cost, status and timestamps. Correct the current author-model/target-model provenance ambiguity.
- Select only authorized ancestors of the admitted branch head, using deterministic topological order and merge deduplication. A sibling's content must never appear merely because it is chronologically nearby. Shared-prefix checkpoints may be reused on descendants whose hashes still match. Branch edits invalidate only dependent checkpoints. Explicit merges need provenance and conflict labels; do not turn mutually exclusive alternatives into one asserted decision.
- Treat a tool invocation and its results, errors, outstanding approvals and required provider reasoning/signatures as an atomic retention group. Never leave a result without its call, split parallel results from their shared call turn, summarize away an unresolved approval, or repeat a side-effect tool to reconstruct lost context. Keep current-turn tool exchanges verbatim until the group is settled. Store full tool output durably and expose bounded model-facing extracts with retrieval references before the next request. UI/storage truth must not be replaced with a 500-character truncation.
- Retain source attachments and citations by authorized stable IDs/content hashes, not expiring signed URLs or copied raw base64 in a summary. Include what each file contributed and page/section references. A reference is only useful if the model has a working authorized retrieval tool; otherwise inline the needed excerpt or explain what cannot be recalled. Do not delete attachments because their messages moved out of active context.
- Prompt the summarizer with an explicit **token budget** and schema for user goal, non-negotiable constraints, accepted decisions, corrections/superseded facts, unresolved questions, completed actions with outcome, pending actions/approvals, entities/IDs, source references and uncertainties. Preserve user instructions as instructions only at their original authority; tool/web text and summary content remain untrusted data, never promoted to a system instruction. Do not store hidden chain-of-thought as a portable summary.
- Chunk oversized source history on complete semantic/tool boundaries, then combine summaries with an auditable coverage manifest. Do not replace the first-16K loss with a last-16K loss. A summary-of-summary may be needed, but record its lineage and periodically regenerate from original sources to limit accumulated errors. The summarizer's own input and output must fit its model budget.
- Validate schema, nonempty content, coverage manifest, source reference authorization, target token budget and material reduction before publishing. Check expected constraints/corrections against source-linked fixtures. A checker model can detect some omissions but is not a guarantee of truth; its calls need authorization, budget and separate usage. On validation failure keep the prior context plan intact.

#### Proposal C: trigger lifecycle, hysteresis and failure behavior

1. Admit the user turn once with a stable request/run ID. Persist `queued -> planning -> compacting -> generating -> terminal` progress; page refresh or another client must observe the same operation. The UI must not own the trigger.
2. Acquire an owned generation/context lease transactionally, with `runId`, lease token, transcript/branch revision and context epoch. Use compare-and-swap publication. Extend a healthy lease via progress heartbeats; the existing fixed 60-second age alone is insufficient for summary calls. Choose one lock acquisition order to avoid compaction-generation deadlocks.
3. Use an idempotency key such as `owner + conversation + branch-prefix-hash + priorCheckpoint + promptVersion + summaryBudgetClass`. Duplicate tabs/actions share one operation/result. Target budgets can differ; reuse only a checkpoint whose actual size fits the target, and validate each pending request again. Stale workers cannot publish or release a newer lease.
4. Compaction publishes a checkpoint and swaps the branch's context pointer atomically after validation. Original messages are untouched. Background work may cover a sealed prefix while new messages append, but install only if that prefix still matches; new suffix stays verbatim. Never let a summary from branch A replace branch B's context.
5. Suggested hysteresis for experiments: trigger near 80%, compact enough to return below roughly 55-65% usable input, and require new covered history/material growth before recompacting. These are candidate values, not user requirements. Suppress repeated no-progress compaction of the same prefix; bound automatic attempts per run and enforce a cooldown/backoff after failure. No cooldown can bypass the hard-fit guard.
6. After tool completion, recompute next-step occupancy using **actual model-facing output**, including parallel result totals. Reserve size before admitting a tool if its response can be large, then store/extract/page before continuation. If there is no settled older prefix to summarize, bound the new tool data instead of compacting half a call/result pair.
7. On transient summary failure, use bounded exponential backoff/jitter under the same source snapshot and lease. Keep old context; continue without compaction only if it still fits the hard guard. If not, preserve the pending user turn, show a recoverable "Couldn't prepare context" state, and offer retry, explicit model change, smaller attachment scope or new chat. No silent last-N fallback and no blind resubmission of side effects.
8. Stop/cancel propagates to summary/count/provider calls where supported and checks durable run ownership before publication and before launching the answer. A late result may settle usage but must not replace context or restart generation. Unknown interrupted provider usage is marked estimated/unknown, not silently free. Recovery marks stale operations without deleting source messages or claiming rollback of completed external actions.

#### Proposal D: stable prefix and cache policy

Use cache stability as an optimization **within correct instructions and authorization**, not as permission to keep stale state.

1. Compose a deterministic base policy/capability prefix, stable per-user/project/conversation instructions, stable skill manifest and tool schemas, a versioned context checkpoint, append-only retained history, then per-turn ephemeral context and the new request. Provider APIs may render tool schemas before system messages; fingerprint that actual order. Keep explicit instruction precedence intact rather than relying on "later system messages always win".
2. Remove fresh ISO datetime from the early base prefix. Put current time/locale/budget warnings/retrieved turn context near the changing suffix in a trusted role permitted by the specific provider, or call a datetime tool. Keep original message timestamps stable, including timezone formatting; do not rewrite old timestamp strings each turn. Evaluate behavior when moving instruction sections.
3. Give base prompt, personalization, project instructions, memory snapshot, summary schema, tool manifest and activated skill bundle explicit versions/content hashes. Stable order within each set; deterministic tie-breaking for memory and integration order. Do not sort semantic message history or rewrite JSON property order arbitrarily between turns. Keep activation append-only where a provider supports it, or intentionally start a new context epoch when the tool/skill set changes.
4. Do not enable every integration/skill to improve a hit rate. A large unused stable tool prefix costs context and may create unsafe capability exposure. Keep a small stable core plus explicit, least-privilege task activations; pin an activation for the current run/epoch. Never retain revoked tools or stale instructions for caching. New provider append-only tool-update APIs are optional adapter experiments, not portable baseline behavior.
5. For Anthropic, experiment with a stable-system breakpoint and a rolling conversation/checkpoint breakpoint, within four slots/20-position lookback. Separate long-lived stable material from short-lived chat material, respecting TTL ordering. For current OpenAI families that support explicit mode, mark useful stable prefixes and avoid writing volatile suffixes. For earlier OpenAI use a stable scoped cache key and supported retention. Gemini starts with implicit caching; explicit objects are an opt-in document-reuse experiment on supported generateContent models.
6. Build cache identity from authenticated scope plus provider organization/workspace/project, credential reference/version, region, actual model/version, API kind, gateway/host route, prompt/tool/memory versions and context epoch. Use opaque HMAC identifiers rather than raw email, prompt text or user IDs in provider cache keys/logs. A key is not an ACL; request construction and retrieval still enforce access every time.
7. Provider workspace/org isolation does not isolate app users sharing credentials. Do not share caches containing private user data across users. On OpenAI use separate scoped keys consistently. Where there is no per-user cache-key control, assess a stable opaque scope discriminator before private content or stronger provider project/workspace separation. Do not claim the discriminator provides a contractual provider security boundary. Public identical base text may be reusable only under an explicit policy; no shared private-document cache or cross-tenant result memoization.
8. Incognito/retention policy applies to summaries, checkpoints, provider-side state, stored responses and explicit caches as well as transcripts. Prefer short approved TTLs and explicit stateless settings when required. Do not activate 12h/24h retention or stored Interactions just to increase hits. Document that provider minimum TTLs are not immediate-delete promises. Delete owned explicit Gemini cache objects on revoke/delete/expiry policy where supported; authorize references and track cleanup failures.
9. Compaction changes a long cache prefix. Preserve independent stable-prefix breakpoints and publish a summary only when it materially reduces context. Do not rewrite the rolling summary on every turn. Cached 100K input may be cheaper than an eager summary plus cache rebuild for a short-lived chat; capacity/quality come before preserving cache hits.

- A model switch starts a target context plan. Recount with its tokenizer/media rules; reject or compact before the call if it is smaller. - Comparison siblings can share an immutable application checkpoint if source scope and permissions match, but each uses its own target budget and accounting. ### Gaps

- Exact trigger, low-water mark, recent-tail budget, summarizer model and summary token budget remain proposals. No benchmark supports choosing fixed values yet. BK should choose default-on behavior and acceptable preparation latency after seeing synthetic UX and measured cost/quality results.
- Provider caching is probabilistic or lifecycle-managed, depending on API. The app cannot infer a hit from a stable prefix hash alone. Actual usage fields, resolved host and price-version evidence are required.
- Perfect semantic preservation is impossible to promise from a lossy summary. The safety contract is immutable originals, explicit coverage/provenance, bounded summaries with quality checks, accessible source retrieval, reversible context selection and a visible failure path.
