# blah.chat dependency, security, and toolchain update paths

Research date: **2026-11-03**. Live npm registry packuments, exact-version metadata, upstream releases/docs, and the local Bun lockfile were checked. All registry versions below were observed on this date, not inferred from search results. Final Next/analyzer registry recheck: **16:22 UTC**. These are research recommendations, not an implemented or validated upgrade.

## 1. What is actually installed, and which update targets are verified?

### Takeaway

The application already uses Next 16, React 19, AI SDK 6, and current-generation Convex. Prioritize security fixes within those lines; treat AI SDK 7, Clerk Core 3, TypeScript 7, and Expo SDK changes as separate migrations. An important same-day exception is Next: 16.4.4 is the observed latest release, but upstream explicitly says it **does not include** the November 3 security release. [Next release](https://github.com/vercel/next.js/releases/tag/v16.4.4)

### Cited Findings

### Inferences

- The declared AI SDK `^6.0.3` is not evidence that version 6.0.3 is installed: the security-relevant resolution is 6.0.89 and provider-utils 4.0.15. Refresh the coordinated AI SDK 6 cohort rather than prescribing an unnecessary major migration. [Lockfile](../../bun.lock), [AI 6 target metadata](https://registry.npmjs.org/ai/6.0.322)
- Root resolutions and workspace-specific React versions need explicit policy, but the lockfile disproves the simplistic claim that mobile necessarily runs the root React version. Inspect actual Metro resolution before changing React globally. [Root](../../package.json), [mobile](../../apps/mobile/package.json), [nested lock entries](../../bun.lock)

### Gaps

- No claim that a registry target is already deployed, fully compatible, or vulnerability-free. Deployment state, native runtime resolution, and baseline test results belong to other research/verification work.
- Convex 1.49.0 is verified from npm, but guessed GitHub release URLs returned 404; its complete release changelog remains a review gate. Next/analyzer 16.4.4 were both independently verified, but a later same-day security release would need a new paired version check.
- This report prioritizes the production stack and Bun/JS toolchain. Tauri's Rust graph, CocoaPods, Android/Gradle, browser binaries, and separately managed experiments were not vulnerability-audited.

## 2. What security risks are supported by the resolved graph and public advisories?

### Takeaway

There are concrete advisory matches, not just old-version concerns. The highest-priority application-facing work is Mermaid and provider-utils, followed by document-ingestion dependency paths and a carefully scoped KaTeX migration; Vitest fixes are primarily development-server hygiene. The audit response contained low/moderate findings, not high/critical findings, which is not proof that the application has no serious exploitable issue. [Bun audit behavior](https://bun.com/docs/pm/cli/audit), [lockfile](../../bun.lock)

### Cited Findings

#### Read-only audit evidence and limitations

- Ran **`agent-work run -- bun audit --json`** against the existing root `bun.lock` with Bun **1.3.14**. It returned advisory JSON and exit code **1** (findings). No `install`, update, audit-fix, build, or test command was run. Bun documents plain audit as lock-aware and non-mutating. [Audit documentation](https://bun.com/docs/pm/cli/audit), [lockfile audited](../../bun.lock)
- Also attempted **`agent-work run -- bun audit --prod --json`**. It returned the same package/advisory set, including Vitest. The local **1.3.14** `bun audit --help` lists only JSON, severity, and ignore flags, not `--prod`. Therefore that second result is **not accepted as a production-only audit**; current online docs describe a newer CLI. Production/dev classification below comes from manifest ownership, parent dependency edges, and advisory prerequisites, not this unsupported filter. [Current docs](https://bun.com/docs/pm/cli/audit), [manifests](../../package.json), [web manifest](../../apps/web/package.json), [lockfile](../../bun.lock)
- Root overrides are not a security certificate: they pin esbuild 0.28.0, protobufjs 7.6.1, minimatch 3.1.4, Vitest/coverage 4.1.8, and many other transitive packages. Several pinned versions now match advisories, and the global minimatch 3 override is applied beneath parents declaring newer majors. [Overrides](../../package.json), [actual edges](../../bun.lock)

## 3. In what sequence should updates ship, and what are the compatibility/rollback gates?

### Takeaway

Use small dependency cohorts and preserve durable Convex generation, auth refresh, persisted messages, token/cost accounting, and native binary compatibility. First establish reproducible supported runtimes, apply narrowly verified security fixes, then migrate APIs independently; do not make framework adoption or an all-latest lockfile rewrite a prerequisite. [Project constraints](../../AGENTS.md), [runtime requirements](https://docs.convex.dev/functions/runtimes)

#### Rejected alternatives and downgrade/rollback gates

- **Reject `bun update --latest` or `bun audit fix --latest` across the workspace.** That would combine unrelated AI, auth, native, compiler, and renderer migrations, and current Bun docs explicitly describe audit-fix rewriting even exact pins/overrides. This assignment authorizes research, not installation. [Bun audit semantics](https://bun.com/docs/pm/cli/audit)
- **Reject framework churn** such as moving to TanStack Start, another router/database, or replacing durable Convex generation with browser-owned AI SDK streaming just because new packages exist. No evidence in this dependency review establishes a need for that architectural replacement. Preserve the project's durable-generation contract. [Project rules](../../AGENTS.md)
- **Reject adopting canary/beta as a security shortcut**, forcing OpenRouter 3 into AI6, globally forcing file-type 22 into older consumers, or upgrading React Native outside Expo's matrix. Stable compatible maintenance targets or a documented migration are available for many actual issues. [OpenRouter peer](https://registry.npmjs.org/@openrouter/ai-sdk-provider/3.1.0), [OfficeParser old edges](../../bun.lock), [Expo version map](https://raw.githubusercontent.com/expo/expo/sdk-54/packages/expo/bundledNativeModules.json)
- **Rollback unit:** each cohort needs its exact previous manifests, lockfile, Bun version, runtime configuration, generated-code baseline, and deployed artifact recorded. Prefer a normal revert of the owning implementation commit, never a reset of unrelated user work. Test the prior build with frozen lockfile under its prior runtime before calling it a viable fallback. Bun 1.4's resolver/lockfile changes make rollback of only `packageManager` insufficient. [Bun release behavior](https://bun.com/blog/bun-v1.4.4), [current CI](../../.github/workflows/ci.yml)
- **Security downgrade gate:** do not silently restore an advisory-matched version when a new release fails. Either use another verified patched version in the same line, or apply a documented mitigation/disable the affected feature and record temporary risk acceptance. For example Mermaid's owner documents sandbox rendering as mitigation; KaTeX explicitly requires eliminating upstream prototype pollution and/or sanitizing output. [Mermaid mitigation](https://github.com/mermaid-js/mermaid/security/advisories/GHSA-ghcm-xqfw-q4vr), [KaTeX mitigation](https://github.com/KaTeX/KaTeX/security/advisories/GHSA-238p-pmpm-9mq7)
- **State and binary rollback gate:** retain backward-compatible persisted message/tool/usage shapes across an AI SDK deployment; do not drop or rewrite old records merely to make a new SDK pass. Convex Node runtime switches can run new code on the old Node version for a few minutes, so test that overlap. Native Expo/module changes require a matching binary/runtime version; do not ship a JS-only update to older binaries without compatibility proof. [AI migration](https://ai-sdk.dev/docs/migration-guides/migration-guide-7-0), [Convex runtime overlap](https://docs.convex.dev/functions/runtimes), [Expo native upgrade guidance](https://docs.expo.dev/workflow/upgrading-expo-sdk-walkthrough/)
- **Release gate:** baseline owner runs the existing typechecks, lint, tests, production build and E2E checks; this researcher intentionally did not duplicate them. Require targeted tests for durable generation after refresh, cross-provider tool/reasoning/cost accounting, Clerk/Convex token refresh, renderer security fixtures and long-message behavior, document ingestion, and native recording/deep links for affected cohorts. Run heavy checks through `agent-work`, with no more than four workers, as the repository requires. [Project rules](../../AGENTS.md), [workspace scripts](../../package.json)
