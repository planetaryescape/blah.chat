# Chat rendering prior art and compatible modernization

Research cutoff and access date: 2026-11-03. This is a source review, not a deployed-app audit. No application changes, installs, builds, benchmarks, or authenticated browsing were performed. Local observations refer to the checked-out repository, not proof that production deploys precisely this revision. Proposed budgets and fixtures below are not measured results.

## What should change in the existing renderer, and what is already good?

### Takeaway

Keep the current chat architecture and repair its rendering contract. The highest-value work is restoring explicit sanitization, making short/long and streaming/completed messages behave consistently, and fixing existing code/citation controls before adding a UI framework.

#### Source-level correctness and security gaps

1. The custom rehype array is `[rehypeRaw, [harden, ...]]`; it omits `rehype-sanitize`. Streamdown 2.2.0 uses the supplied array in place of its default raw/sanitize/harden chain. The current official security guide explicitly warns that `rehypePlugins` replaces the entire default array. Restoring sanitization is warranted without claiming a demonstrated executable XSS payload. The `bible:` allowance must be made in both sanitizer schema and URL policy, not by dropping the sanitizer. [Local configuration, lines 22-36 and 413](../../apps/web/src/components/chat/MarkdownContent.tsx), [installed-version upstream source](https://github.com/vercel/streamdown/blob/streamdown%402.2.0/packages/streamdown/index.tsx), [official security guide](https://streamdown.ai/docs/security).

2. Small/streaming math is wired as if it were built into Streamdown. No `plugins.math` or equivalent remark-math/rehype-katex configuration is supplied. In the installed 2.2.0 source, math plugins are appended only when `plugins.math` exists. Loading `mhchem` does not attach a Markdown math parser. Long completed messages use a different worker tokenizer, `trust: true`, and a simplified chemistry macro. This is a concrete integration mismatch to reproduce, not an argument for adding a second renderer. [Local renderer, lines 102-106 and 406-434](../../apps/web/src/components/chat/MarkdownContent.tsx), [worker, lines 178-245](../../apps/web/src/lib/markdown/worker.ts), [2.2.0 plugin handling](https://github.com/vercel/streamdown/blob/streamdown%402.2.0/packages/streamdown/index.tsx), [math plugin implementation](https://github.com/vercel/streamdown/blob/2dbe48b4403d8e67ac16c99168aa7cfb4cd98c26/packages/streamdown-math/index.ts).

3. The completed-message worker returns HTML wrappers, not `CodeBlock`, `MermaidRenderer`, or `BibleVerseLink` components. Its Mermaid output is a `mermaid-placeholder` pre element, with no hydration path in the inspected renderer. Code copy/wrap controls and Bible popup behavior therefore have no equivalent in that HTML branch. Worker failures fall back to Streamdown, so behavior also varies by worker availability. Current hook tests mock the worker and assert threshold/caching, not cross-renderer interaction parity. [Worker, lines 256-311](../../apps/web/src/lib/markdown/worker.ts), [HTML replacement branch](../../apps/web/src/components/chat/MarkdownContent.tsx), [existing tests](../../apps/web/src/hooks/__tests__/useWorkerMarkdown.test.ts).

4. Code wrap toggles only local button state; it does not change any pre/code style or communicate with `CodeBlock`. Copy does not catch clipboard rejection. Both controls are opacity-zero except on group hover. `CodeBlock` can keep previous highlighted HTML while the `code` prop has already advanced, so visible content and copied content can temporarily differ. The custom Markdown `code` component infers inline versus fenced from language/class presence and ignores Streamdown's block marker; unlabeled fences and identifiers such as `c++`/`c#` deserve explicit fixtures. [Controls](../../apps/web/src/components/chat/ClientCodeControls.tsx), [code block, lines 33-69 and 91-115](../../apps/web/src/components/chat/CodeBlock.tsx), [Markdown code override, lines 114-154](../../apps/web/src/components/chat/MarkdownContent.tsx).

5. Citation preprocessing turns every prose `[n]` into `#source-n`, even without an actual source record, and uses regex code-region protection that only covers closed triple-backtick and simple inline spans. It does not cover tilde fences, longer fences, incomplete fences or all existing links. The click handler globally queries that fragment. `SourceList` renders its cards only when expanded and does not assign matching `source-n` IDs. This needs message-scoped source resolution and expansion, not just styling. [Preprocessing and anchor handler](../../apps/web/src/components/chat/MarkdownContent.tsx), [source list](../../apps/web/src/components/chat/SourceList.tsx).

6. `createMarkdownComponents` creates new component functions on every render. Streamdown's 2.2.0 block comparator examines component identity, so this weakens the memoization already present upstream. The exported `MarkdownContentMemo` is not what `InlineToolCallContent` imports; each text/tool segment uses `MarkdownContent` with an index-derived key. Stabilizing map/functions is a small, compatible change; restructuring message ownership is not required. [Renderer, lines 114 and 326-327](../../apps/web/src/components/chat/MarkdownContent.tsx), [actual caller](../../apps/web/src/components/chat/InlineToolCallContent.tsx), [upstream block comparator](https://github.com/vercel/streamdown/blob/streamdown%402.2.0/packages/streamdown/index.tsx).

### Inferences

Recommended sequence, with each step small enough for an independent PR:

1. Restore a tested sanitize/harden chain. Define one URL/image/custom-protocol policy for both rendering paths. This is security-relevant repair, not a visual redesign.
2. Make one semantic rendering contract. First stop routing rich messages to a behavior-changing HTML fast path, or return typed blocks/tokens that still render through the existing components. Retain a worker for expensive highlighting/parsing only where parity holds. Wire math explicitly and share preprocessing/language policy.
3. Repair wrap/copy/fence handling and message-scoped citations. Memoize component maps/configuration; use raw source for copy/download, never highlighted DOM text. Keep plain text available while highlighting is delayed.
4. Evaluate Streamdown 2.7.1 in isolation. Keep custom components unless an upstream component demonstrably satisfies the same behaviors. Compare the custom highlighter with the incremental plugin or a worker-only highlighter; do not add both by default.
5. Tune scroll/virtualization only after instrumentation. Use content size/DOM cost alongside group count when evaluating the threshold.

The single-dollar-math exclusion, dark/code-editor visual language, custom Bible links, multi-model comparison and diagram code preview while streaming are intentional product choices. Missing math wiring, controls that do not affect the code, dangling citations and threshold-dependent feature removal are behavioral issues. Do not present disagreement with an intentional choice as a bug.

### Gaps

- No runtime reproduction, production bundle analysis, browser accessibility session, or deployed-version verification. Severity reflects source-level risk, not proven exploitability or measured user incidence.
- The default plugin mismatch strongly predicts short-message math failures, but no screenshot or DOM assertion was collected.
- No migration to Shiki 4 was exercised. Current imports, transformed grammar compatibility, Node/Bun requirements and extension support need a compatibility spike.
- Code comments claiming 60% mobile savings, 60fps, 50ms parsing, or particular Mermaid bundle sizes are not benchmark evidence. They were not independently verified.

#### Append-only rendering is conditional, not a Markdown law

- Streamdown's release describes reusing parsed blocks and its code implementation reuses completed-line token rows. Those are concrete incremental strategies; they do not mean arbitrary Markdown can be frozen after every newline. Reference-link definitions and footnotes can affect earlier content. Streamdown 2.7.1 specifically fixes reference definitions in another block by retaining that document in one block. [2.7.0](https://github.com/vercel/streamdown/releases/tag/streamdown%402.7.0), [2.7.1](https://github.com/vercel/streamdown/releases/tag/streamdown%402.7.1).
- blah.chat's citation/Bible preprocessing can rewrite previously displayed text, and `useStreamBuffer` explicitly resets on nonappend changes. `InlineToolCallContent` also slices Markdown at tool positions. Incremental caches must invalidate on transformed-prefix changes and must not assume every tool boundary is a syntactically closed Markdown boundary. [Preprocessing](../../apps/web/src/components/chat/MarkdownContent.tsx), [buffer, lines 78-100](../../apps/web/src/hooks/useStreamBuffer.ts), [tool segments](../../apps/web/src/components/chat/InlineToolCallContent.tsx).
- The app's Markdown cache uses only a 32-bit hash as the key, with no full-content equality check, 200 entries and a five-minute TTL. That is a content-correctness risk under collisions and an imprecise memory bound for large responses. Current upstream code caching includes the full code in its key and accounts for result size. [Local cache](../../apps/web/src/lib/markdown/cache.ts), [upstream cache](https://github.com/vercel/streamdown/blob/2dbe48b4403d8e67ac16c99168aa7cfb4cd98c26/packages/streamdown-code/index.ts).

#### Scroll, mobile keyboard and accessibility

- Current scroll intent distinguishes wheel/touch/pointer upward movement, provides jump-to-latest, and restores per-conversation position. Its listeners do not explicitly classify keyboard PageUp/Home/Arrow scrolling, and the effect binds to `scrollerRef.current` without depending on scroller replacement. Test keyboard reading and the 499-to-500 mode transition before deciding on a repair. Virtuoso `followOutput` returns `"smooth"` even though reduced motion is handled in several other scroll paths. [Intent hook](../../apps/web/src/hooks/useScrollIntent.ts), [list, lines 29-99 and 314-350](../../apps/web/src/components/chat/VirtualizedMessageList.tsx).
- `useIOSKeyboard` already listens to `visualViewport.resize` and uses a 150px height-difference threshold; `ChatInput` calls it without using the returned state or supplying callbacks. The hook's presence alone does not prove keyboard avoidance. MDN documents that both pinch zoom and the on-screen keyboard affect the visual viewport, and exposes scale/offset/scroll information. Verify layout before adding more keyboard heuristics. [Local hook](../../apps/web/src/hooks/useIOSKeyboard.ts), [composer](../../apps/web/src/components/chat/ChatInput.tsx), [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Visual_Viewport_API).
- History has `role="log"`, polite live updates and `aria-busy`; the page also has a dedicated status announcer. `useMessageAnnouncer` tracks count/last ID, not previous status. An assistant message that appears while generating and later completes with the same ID does not satisfy its `isNewMessage` guard. Test one completion announcement, cancellation/error announcements and duplicate speech between the two regions. [Announcer](../../apps/web/src/hooks/useMessageAnnouncer.ts), [page status element](../../apps/web/src/app/%28main%29/chat/%5BconversationId%5D/page.tsx), [history roles](../../apps/web/src/components/chat/VirtualizedMessageList.tsx).
- WCAG status-message guidance calls for conveying status without taking focus or unnecessary interruption. WCAG 2.2's minimum pointer target is 24 by 24 CSS pixels, subject to listed exceptions; 44px may be a product target, not that criterion's mandatory minimum. Source-only inspection does not establish conformance. [Status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html), [target-size minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html).

### Inferences

Use a single owner for scrolling in each list mode. Follow output only while the reader is following; stop on deliberate keyboard/wheel/touch movement or selection; resume on explicit jump. Image/math/diagram expansion and composer resizing must preserve either the bottom position or the reader's anchor. Avoid multiplying timers and independent scroll effects.

Keep completed React message subtrees stable. Update only active message segments, use stable IDs instead of index keys where practical, and retain text-selection/focus across streaming updates. For the nonvirtual mode, evaluate `content-visibility` only as a measured alternative with accessibility/find-in-page fixtures, not as an automatic improvement.

The existing whitespace buffer can hold a whitespace-free 50-99-character tail until more input arrives, then emits 100-character slices; those slices use UTF-16 boundaries. Prefer grapheme-aware segmentation, a maximum reveal lag and immediate final flush. CJK parsing and IME composition are separate from this display scheduling problem. [Buffer implementation](../../apps/web/src/hooks/useStreamBuffer.ts).

#### Proposed benchmark spike, not measured results

Compare the current baseline with two separately implemented candidates: stable component/config identities plus unified semantics, then incremental or worker-based highlighting. Use the same captured content/chunk schedule and browser/device conditions for each.

- Fixtures: prose/code/math/table/diagram mixes at 5k, 50k and 250k characters; 50/250/499/500/1000 grouped rows; ten very large messages; two/four simultaneous comparison streams. Include 10/40/100 chunks per second, burst delivery, pause/resume, background tab, final flush and nonappend edits.
- Measure cold and warm loads separately. Report device, browser/build, CPU throttling, viewport, network setting, fixture commit, chunk schedule, repetitions and median/p95. Desktop browser throttling is not a substitute for at least one real lower-end mobile device.
- Capture React commits and which rows rerender; parser/tokenizer/sanitizer/DOM-insertion time separately; long tasks; input-to-paint latency; rendered-versus-persisted text lag; scroll anchor displacement; worker queue depth and stale work; DOM nodes; heap growth; initial/lazy compressed JS by feature.
- Proposed starting gates: no application-attributable streaming main-thread task over 50ms on target hardware; active-message commit p95 below 16ms desktop and 32ms mobile; composer interaction p95 below 100ms in the deterministic fixture; visual reveal lag below 250ms with zero lag at completion; reading-anchor displacement no more than 2 CSS pixels for updates below it. These are negotiation targets, not established app metrics.
- Proposed resource gates: do not regress initial compressed chat JS by more than 20KiB without an explained tradeoff; keep Mermaid and uncommon grammars out of initial plain-text-chat loading; one shared rendering/highlighting worker initially; bounded queues and content-sized caches. Heap should plateau under repeated mount/unmount/stream cycles after collection, rather than grow with obsolete transient results.
- Use existing Vitest and Playwright infrastructure. A full browser trace and production bundle comparison are future authorized work, not something run during this assignment. Do not quote upstream release claims as an app speedup ratio.

### Gaps

- No library or app was benchmarked. Upstream performance descriptions identify mechanisms, not comparable speed measurements with a documented shared method.
- Public app source demonstrates reusable patterns, not proof of production traffic scale, reliability or accessibility.
- No reason was established to adopt assistant-ui's runtime or AI Elements wholesale. A migration cost estimate would need an adapter prototype and a full inventory of branch/comparison/tool/attachment behavior.
- No physical mobile keyboard, VoiceOver, TalkBack, NVDA, clipboard-denial, selection or virtualization test was run.

## What safety policy and acceptance fixtures should gate the upgrades?

### Takeaway

Treat generated Markdown, fetched sources, math, diagrams and executable artifacts as different trust boundaries. Make fixtures assert behavior at every partial-stream prefix and after completion, including both sides of the worker and virtualization thresholds.

### Cited findings

#### Security-relevant rendering sinks

| Sink | Observed boundary | Compatible policy to test |
| --- | --- | --- |
| Raw Markdown HTML | Custom rehype chain omits sanitization and passes parsed HTML into React. `harden` controls URLs but is not the missing HTML allowlist. [Local renderer](../../apps/web/src/components/chat/MarkdownContent.tsx), [official replacement warning](https://streamdown.ai/docs/security). | Retain an explicit HTML allowlist, or disable raw HTML if the product does not need it. Allow `bible:` only in the specific link position; no event attributes, scripts, embedded forms/frames or arbitrary style/ID escape. |
| Worker HTML insertion | `dangerouslySetInnerHTML` receives DOMPurify output. Sanitization actually runs on the main thread, despite an outdated renderer comment claiming it runs in the worker. Worker HTML construction interpolates unescaped fields in several custom renderers. Sanitizer configuration includes `ADD_URI_SAFE_ATTR: ["href"]` and a custom URI regex, which should be reviewed rather than assumed equivalent to the React path. [Hook](../../apps/web/src/hooks/useWorkerMarkdown.ts), [worker](../../apps/web/src/lib/markdown/worker.ts), [insertion](../../apps/web/src/components/chat/MarkdownContent.tsx). | Escape text/attributes when constructing HTML, retain final sanitization and enforce the same URL/image policy. | Highlighted code HTML | `CodeBlock` inserts highlighter HTML; fallback escapes all source characters. [Code block](../../apps/web/src/components/chat/CodeBlock.tsx), [highlighter](../../apps/web/src/lib/highlighter.ts). | Keep source text as data, never evaluate code/MDX. Async effects do not guard stale results, and a new config object is passed from the Markdown override. The effect can still do work during streaming despite the UI returning a code preview. [Renderer](../../apps/web/src/components/chat/MermaidRenderer.tsx), [caller](../../apps/web/src/components/chat/MarkdownContent.tsx). | Explicit strict security, review directive/config overrides, size/edge/time limits and a plain-code fallback. #### Artifact isolation prior art, only if live preview becomes a requirement

- Hugging Face preview builders deliberately omit `allow-same-origin`, popups, downloads and modal permissions. The panel validates `event.source === iframe.contentWindow`, a per-preview channel, payload shape, external URLs and user activation for external navigation. This is useful concrete prior art, not a recommendation to adopt all its allowed capabilities or CDN dependencies. An opaque origin alone does not prevent network exfiltration or CPU denial of service. [Builder](https://github.com/huggingface/chat-ui/blob/70f00f5ecc64e6048a77b093020a47c62170fbd8/src/lib/utils/previewSrcdoc.ts), [host validation](https://github.com/huggingface/chat-ui/blob/70f00f5ecc64e6048a77b093020a47c62170fbd8/src/lib/components/chat/ArtifactPanel.svelte).
- assistant-ui's Safe Content Frame uses a separate public-suffix-backed per-render domain and origin-checked messaging. Its documentation explicitly says that network access is not restricted and warns about self-hosting without the same isolation properties. That is a separate deployment/security decision, not a drop-in Markdown component. Do not transmit conversation secrets to generated code just because it runs in a sandbox. [Design and limitations](https://github.com/assistant-ui/assistant-ui/blob/a96e62f89da310602b716821dd91b9525f94cbb5/apps/docs/content/docs-sites/safe-content-frame/how-it-works.mdx).

### Inferences

#### Acceptance fixture matrix

These are proposed tests, not reported passes. Run applicable content with 1-character, random-size and burst chunking, at every prefix near a delimiter, and then as completed text. Repeat at 4,999/5,000/5,001 code units, with workers disabled/timed out, and with citations/tool segments present.

Block stays a block without a language. Unknown/partial languages show escaped text. Completion does not duplicate content or lose controls. |

Recommended code-control behavior is modest: visible or focus-revealed copy/wrap/download controls, a filename/language label when known, raw-source copy, optional text-file download with sanitized filename, and success/error status. Download is a new capability for code blocks, not a repair to an existing code-download feature. Do not add a heavyweight editor to ordinary code fences.

For citations, pass a typed source map and message ID into rendering. Prefer a text-node/AST transform that skips code/math/link nodes and checks actual source existence. Avoid inferring provenance from arbitrary numeric brackets. For long responses, keep the same accessible React components while background work produces data, rather than using HTML length as the feature switch.

### Gaps

- Security-sensitive findings identify sinks and missing/unequal policies. No exploit, advisory match or security certification was established. A follow-up should verify payloads with network interception, CSP and real DOM/browser behavior.
- Existing artifact cards are document navigation, not executable previews. The isolation discussion is preventative guidance for a future feature and must not be reported as an existing vulnerability.
- A complete security review would also inspect backend source enrichment/proxy/attachment URL generation and canvas/editor sanitization. Those are outside this rendering-focused assignment.
- All linked official pages/repositories/releases were accessed 2026-11-03. Public implementation links use cutoff-compatible commit IDs where inspected; release links distinguish released functionality from current-main source. Streamdown main may include unreleased changes after 2.7.1, so confirm APIs against the chosen package before implementation.
