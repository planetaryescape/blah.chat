# Routing and feature disposition

## 1. What does the current product actually route, and what exactly is Smart Assistant?

### Takeaway

Smart Assistant is the separate meeting-recording/transcript-to-tasks-and-notes workflow at `/assistant`. Its removal is approved. Core chat tools, transcription, tasks, notes, projects, memory, and model recommendations are separate features and must survive. The current Auto implementation needs correctness repairs before a more sophisticated routing algorithm: it has a direct-provider bypass, incomplete routing inputs, disconnected seed embeddings, and unconstrained last-resort fallbacks. [Assistant page][assistant-page]; [router wrapper][auto-wrapper]; [classifier action][classifier-action]; [generation][generation].

Scope: read-only source inspection on 2026-11-03 against the coordinator's baseline `04866f80a6236716ebf8d8c5a79001727f85f4bf`. No source edits, provider calls, installs, heavy checks, commits, or experiment cleanup were performed. Only this note is an output. The repository has existing untracked experiments; they are outside the audited product. [Baseline](baseline.md).

### Inferences

- Priority is a constrained selection contract, not replacing regexes with an ML service. Today a more accurate classifier can still select an unavailable model, lose sticky state, or have its choice bypassed by a direct key. [Wrapper][auto-wrapper]; [selector][bin-selector]; [generation][generation].
- The complete purge must remove both meeting extraction actions and the legacy review panel, and must move the shared deadline prompt before deleting the extraction prompt module. A single feature-name search is insufficient. [Task manager][task-manager]; [task action][task-action]; [task panel][task-review].
- Historical Smart Assistant outputs are ordinary user tasks/notes now. Removing the feature does not authorize removing that user content. The existing page does not persist enough provenance to reconstruct every output reliably. [Assistant save path][assistant-page].

### Gaps

- No production environment keys, runtime route frequencies, model availability, latency distributions, usage volumes, or deployed seed artifacts were inspected. Direct-provider bypass behavior is confirmed in source/test; whether production currently takes it is unknown.
- No customer BYOD database, pending scheduled functions, old notifications, cached clients, or orphan storage inventory was queried. These must be checked during an authorized migration.
- Absence statements above concern tracked source searches and inspected files, not proof that no external client invokes a public Convex function or a published package subpath.

## 2. What does current routing research and official vendor documentation justify?

### Takeaway

Use a small, well-curated, policy-eligible model pool and evaluate it on blah.chat conversations before adopting a learned router. RouteLLM supports learning when a stronger model is worth using, but newer benchmark evidence warns that sophisticated routers and larger model pools often fail to beat simple baselines. Hosted vendor routing is an optional experiment, not a reason to upload private conversations or abandon local policy enforcement. [Ong et al.][routellm-paper]; [Li et al.][llmrouterbench]; [Not Diamond training docs][notdiamond]; [OpenRouter Auto docs][openrouter-auto].

#### Choosing an algorithm deliberately

| Approach | What it decides | Cost, latency and privacy | Recommended role |
|---|---|---|---|
| Deterministic constraints plus task classifier | Determines what can run, then maps a task label to a curated model set. Current embedding labels are not labels of comparative answer quality. Current hard-rule path unnecessarily pays that hop. | First production repair. Keep categories as a debuggable baseline and improve inputs/constraints, not as a claim of measured optimality. |
| Learned pairwise/value router | Predicts which candidate is likely to be better, or how much quality a stronger candidate adds. RouteLLM's threshold changes the cheap/strong allocation before either answer is generated. [Paper][routellm-full]. | One answer-generation call, plus router inference/embedding overhead. ### Inferences

- Task type and answer difficulty are useful features, but choosing "coding" correctly does not establish that model A beats model B on the code or fits its tools/context. Separate a task classifier score from a calibrated pairwise win probability. [Current classification][classifier]; [RouteLLM formulation][routellm-full].
- Model opt-outs, BYOK boundaries, tool support and context fit must be hard constraints applied outside any learned or hosted router and reapplied on every fallback. A quality estimator should not decide whether it is permitted to disclose a conversation to a provider. [Current selector gaps][bin-selector]; [BYOK configuration][byok]; [OpenRouter restrictions][openrouter-auto].
- The 2026 benchmark supports spending effort on a compact, maintained candidate catalog and representative evals before maintaining several overlapping routing systems. It does not justify importing historical benchmark winners or promising a fixed cost reduction. [Li et al.][llmrouterbench]; [Ong et al.][routellm-full].

### Gaps

- No reviewed paper establishes safe routing for this app's multimodal histories, memory, private retrieval and side-effecting tools. These need application-specific tests.
- Current benchmark models, rate cards, preference distributions and judge behavior can shift. Historical percentage savings and pretrained weights must be revalidated on the deployed pair and full cost model.
- Vendor privacy terms, latency SLAs, supported regions and credentials were not audited. Documentation of a feature is not authorization to send data to it.
- A search surfaced a 2026 latency-aware routing paper whose fetched identifier/submission-date metadata appeared inconsistent. Its numerical claims are deliberately not relied on here. No benchmark/job was run.

## 3. What should be kept, integrated, removed, tested or deferred?

### Takeaway

Execute the complete Smart Assistant retirement as a staged compatibility/data migration, not a UI hide. In parallel, make the existing router enforce one eligibility contract and evaluate deterministic baselines. Add learned routing only if it produces better quality/cost/latency trade-offs on current, approved examples. All dispositions below except Smart Assistant removal are recommendations, not additional BK-approved deletions. #### Safe, complete Smart Assistant removal sequence

This is an implementation plan, not a record of executed changes. Dependencies and retention choices are grounded in the removal map above. No product content deletion is authorized.

1. **Record the retirement contract and inventory.** Freeze the exact path/symbol inventory above; snapshot counts and sums for tasks, notes, usage, preferences and relevant storage; inventory all deployed backends/BYOD versions, published AI prompt consumers and old web/mobile clients. Export a restricted migration manifest with record IDs and old/new values for rollback. No transcript contents or keys in migration logs. Completion: owners can identify each writer and each schema version before touching validators. [Schemas][task-schema]; [usage schema][usage-schema]; [BYOD generator][byod-sync].

2. **Stop entrypoints and producers before contracting schemas.** Remove the UI route, nav and settings. Deploy removal or temporary fail-closed retirement handlers for both public extraction actions so old clients cannot trigger paid extraction. If using a transition handler, it must contain no provider call and have a dated deletion gate; final state deletes the function. Inventory pending/running extraction actions and quiesce only those jobs. Keep shared transcribe/file APIs. Completion: direct invocation by a stale client fails without uploads/extraction/provider requests; no new old-marker rows appear during a monitoring window. There is no feature cron to remove. [Public extraction actions][meeting-action]; [legacy action][task-action]; [crons][crons].

#### Incremental router implementation within current boundaries

The following is a recommended contract and rollout, not a new dependency commitment.

**R0: Repair policy and inputs first.** Retain `packages/auto-router` as pure selection logic and the Convex action as its I/O adapter. Feed the canonical shared/database catalog into its existing `ModelRegistry` boundary. Version/fingerprint the catalog, route bins, examples, embedding model and policy in each decision. The existing factory supports registry overrides but the current backend bypasses them. Validate catalog/bin references against the actual execution adapter, not just router-local existence. [Registry][registry]; [factory][router-factory]; [classifier action][classifier-action]; [execution registry][ai-registry].

Define a `RoutingRequest` carrying explicit-versus-Auto intent, current branch context summary/recent turns, real prompt token estimates, reserved output/reasoning tokens, required input/output types, required tool/schema support, allowed providers/models, opt-outs, available credential mode, budget and latency policy, risk flags, failed IDs, previous model/route and provider/cache affinity. Prefer structured non-sensitive metadata over sending full histories to a classifier. Build independent risk requirements before task matching. An image plus medical advice must satisfy both constraints; a first-match label cannot overwrite either. [Current missing inputs][generation]; [current precedence][hard-rules]; [selector constraints][bin-selector].

All selection and fallback branches must return a policy-eligible candidate or a typed `no_eligible_model` result. Apply the same validator to direct-only mode, disabled-Auto default, classifier-error fallback, missing-bin fallback, provider retries and manual selections. If only one direct model is available, Auto can select it without classification, but must reject unsupported images/tools/context and must not retry an excluded failed model. Keep the no-paid-auxiliary-call behavior as an explicit deployment capability policy rather than a key-presence side effect. [Wrapper][auto-wrapper]; [direct test][direct-test]; [selector last resort][bin-selector].

BYOK must be an execution and routing boundary. Current BYOK settings require a user Vercel Gateway key and expose key-availability flags, but inspected generation calls `getModel(modelId)` and the shared registry chooses environment-backed clients; the router has no BYOK inputs. Do not imply the current Auto path guarantees user-key isolation. Make credential resolution explicit before both auxiliary classification and answer generation. Missing BYOK credentials should fail or ask for permission, never silently spend platform keys/send private content to an unapproved classifier. [BYOK][byok]; [generation, line 640][generation]; [registry][ai-registry]; [classifier embedding/tiebreak][classifier-action].

**R1: Deterministic baseline with honest preferences.** Run cheap hard constraints/rules before embedding. Use the existing `selectModel`/pure selector boundary for curated bins, fix previous-route propagation, and use one tested classifier path. If similarity examples are retained, load a versioned embedding artifact actually consumed by the action or embed them in a separately approved preparation step. Respect `classifierFallbackEnabled` in the no-example branch, where the current code calls an LLM regardless. Report reason codes and distinguish task-label confidence from answer-quality confidence. [Factory][router-factory]; [embedding script][embedding-script]; [classifier no-examples branch][classifier-action].

Estimate request/session cost from uncached input, expected cache reads/writes, expected output, reasoning budget, classifier/retrieval/tool charges and retry allowance. Current `pricing.cached`/reasoning/tier data can inform this, but router-local profiles lack it. Do not sort by `(input + output)/2` for a long input/short-output turn. Use conservative estimates and reconcile against actual usage; an economy preference is not permission to violate context/tool safety. [AI catalog][ai-models]; [router model shape][profiles]; [usage][usage-schema].

Make manual choice sticky by intent. For Auto, keep the prior eligible model/provider until a measured benefit exceeds switching cost or a new requirement forces a change. Consider full multi-turn cost and coherence rather than optimizing one isolated user sentence. Account for lost cached prefixes and provider affinity, but never let cache savings override safety, opt-outs or missing credentials. Persist both the task route and resolved provider/model identity so follow-ups and retries can explain the decision. Existing cached-system-prompt reuse is not itself proof of a provider prompt-cache hit. [Generation prompt cache and routing state][generation]; [OpenRouter cache mechanism][cache-docs].

Use deterministic conservative candidates and explicit escalation/clarification for high stakes. Do not label "premium" as safe, do not explore randomly there, and do not silently relax a provider restriction to find a supposedly safer model. Snapshot policy plus a stable tie-breaker should make routing reproducible. Keep user model opt-outs distinct from transient failed-model exclusions. [Historical premium random behavior][legacy-core]; [current high-stakes patterns][hard-rules].

**R2: Local offline learned-routing spike.** Compare the repaired baseline against a two- or three-candidate current pool, cheapest-eligible, strongest-reviewed and a calibrated pairwise/value predictor. Use the existing selection-return contract to keep durable streaming, cancellation, accounting and retry implementation unchanged. A Python RouteLLM sidecar or converted local predictor is a later engineering choice; there is no need to insert a second generation gateway just to choose an ID. Evaluate router inference/embedding latency and maintenance cost as part of the benefit. [Factory interfaces][router-factory]; [RouteLLM deployment][routellm-repo].

**R3: Approved shadow/canary, then optional expansion.** Shadow means compute/log an alternative selection without executing a second answer or tools by default. Any remote embedding/model call still requires approval/budget. Promotion requires slice-level quality/cost/latency results and a rollback to the deterministic policy. Hosted routers can be separate adapters only after privacy review. Model/provider catalog changes invalidate enough of the evaluation assumptions to trigger replay and small canaries. No online bandit is needed for these phases. [Decision trace][router-types]; [Langfuse offline/online distinction][langfuse-evals]; [new benchmark caution][llmrouterbench].

#### Implementable offline evaluation suite

Start local and dependency-light. Synthetic policy fixtures, deterministic fake adapters and recorded authorized response fixtures can run without network. Propose dataset schema, source mix, metrics and a first 5-12 case review set for BK approval before generating/uploading anything. Then expand to a versioned representative suite, keeping high-risk slices mandatory. This follows Langfuse's distinction between deterministic evaluation, human review and optional judges, not an assumption that every test needs an LLM. [Langfuse overview][langfuse-evals]; [existing pure classifier][classifier]; [direct mock test][direct-test].

Recommended fixture record:

```text
case_id, conversation_family_id, source/consent, split, risk_slice
input: branch history or approved summary, latest message, typed attachments,
       prompt/context/output/reasoning budgets, tool requirements,
       explicit_or_auto, previous model/route/provider, credential mode,
       allowed/blocked models/providers, failed IDs, latency/budget policy
expected: allowed candidate set OR typed failure, required policy behaviors,
          task rubric/reference/validator, reviewed comparative outcomes
metadata: model/provider revision, catalog/policy/prompt/example versions,
          embedding identity/dimensions, cache state, token prices and timestamp
```

Never train on the same conversation families or near-duplicate prompts used to report final quality. Split by conversation and time; hold out new model versions for drift checks. Model comparison votes already contain winner/tie/both-bad, but candidate outputs, full context and model options must be joined from messages. Respect deletion/incognito/consent; model choice, copying or retrying alone is not a clean preference label. Use blinded human pairwise judgments for open-ended prose, deterministic schemas/tests for structured/code tasks, and human-labeled safety/tool policy cases. If using judges, calibrate against reviewed labels and track disagreement/position/model-family bias. [Votes][votes]; [RouteLLM data/generalization limitations][routellm-full]; [Langfuse evaluator options][langfuse-evals].

### Inferences

- The smallest useful modernization delivers fewer parallel decisions: one eligibility filter, one current catalog adapter, one routing reason/trace contract, one evaluation dataset, and recommendations that reuse those calculations. It does not require the most sophisticated published model. [Current duplication][profiles]; [separate triage][model-triage]; [2026 benchmark][llmrouterbench].
- Smart Assistant removal should be independently shippable before a learned-router experiment. The retirement dependency that crosses into chat is the deadline prompt/accounting label, not the underlying chat agent. [Task manager][task-manager]; [triage writes][model-triage]; [page][assistant-page].

### Gaps

- Migration category names, retention duration, backup handling, customer BYOD rollout, acceptable latency/cost ceilings and quality non-inferiority margins still require owner approval.
- The code audit cannot supply user behavior evidence for deleting templates, bookmarks, tasks, projects or other navigation destinations. None is an approved removal here.
- Current model-pair selection requires availability/credential checks and reviewed outputs on representative work. This research intentionally makes no paid calls and does not nominate a historical model ID as the new production default.
